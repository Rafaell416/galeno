# Galeno v0.0.1 — Especificación del MVP
### App de escritorio (Mac) que crea y configura tu agente en Claude Code, para Product Managers

**Fecha:** 2 de octubre de 2026 · **Nombre del producto:** **Galeno**
**Complementa:** `01-plan-producto.md` · `02-perfil-pm.md` · `04-design-system.md`
**Es la fuente de verdad del alcance:** si otro documento dice algo distinto, manda este.

## 1. Decisiones cerradas (no se reabren en v0.0.1)

| Decisión | Valor |
|---|---|
| Nombre | **Galeno**. La app es la marca; cada usuario nombra a *su* agente en el wizard |
| Perfil | **Tres roles: producto, marketing y comercial** (decisión de Rafa, 5 oct 2026; antes solo Product Managers). Dev, legal, salud: después |
| Plataforma | **Solo Mac** |
| Motor | **Solo genera configuración de Claude Code** (Codex/Cursor/Grok: después) |
| Modelo de negocio | **Pago único: USD 200** (precio inicial) |
| Marketplace de skills | **A futuro**, no en v0.0.1 |
| WhatsApp | **Lectura libre y envío con aprobación** (decisión de Rafa, 7 oct 2026, `docs/09`; antes solo lectura, con el envío para v0.2). Un solo envío, `send_message`, texto a una persona o a un grupo del usuario, con guardas en el bridge |
| Varios proyectos | **Un agente por proyecto**, cada uno en su carpeta (`~/Galeno/<agente>/`). En v0.0.1 se pueden crear varios; la **separación garantizada de contexto** entre ellos es v0.2. Ver §3b |
| Envío de mensajes | Por **Slack, email y WhatsApp** (este último solo por `send_message`, siempre con aprobación y con topes en el código; `docs/09` §4) |
| Secretos del usuario | **Nunca tocan infraestructura propia.** Todo local |
| Arquitectura | **La app Mac es la única interfaz del usuario.** Por debajo, un motor (librería/binario interno) genera la config; el usuario nunca lo ve ni lo usa. Motor y app se construyen en paralelo |
| Framework de la app | **Swift + SwiftUI, nativa de Mac.** Rafa ya domina Swift; es la app que mejor se siente en Mac y no requiere Rust ni contenedor web. Trade-off aceptado: no portable a Windows (Mac-only es firme) |

---

**Sobre la arquitectura con Swift:** Galeno.app es un orquestador de procesos. Swift/SwiftUI hace el wizard y genera la config; lanza y supervisa un binario Go para WhatsApp; y corre `claude mcp add` para los MCP hospedados. Ver §4c.

**Sobre la marca:** Galeno es el nombre del producto (la app que crea agentes), no del agente. Cada usuario nombra el suyo. El Galeno de MediClub es el primer agente nacido del producto y sirve como caso de referencia: "el primer Galeno fue el mío, para una clínica". Narrativa: *Galeno te crea tu agente.*

## 2. Qué hace la v0.0.1 (y nada más)

Un usuario con Claude Code instalado abre la app, responde un wizard, y queda con un agente que:

**Lee de:**
- WhatsApp — grupos y chats que el usuario elija (vinculación por QR; lectura libre y envío con aprobación)
- Slack — canales que el usuario elija
- Notion — páginas y bases que el usuario comparta
- Google Drive / Docs / Sheets — carpetas que el usuario autorice
- Jira — proyectos que el usuario autorice
- **Claude Design** — los diseños del usuario: el agente abre el enlace de un diseño, o el nombre de un proyecto, que el usuario le pase. Servidor `api.anthropic.com/v1/design/mcp`, **no verificado**: Claude Code ya lo inyecta solo como `claude_design` y Anthropic no lo documenta como servidor que se registre; hay reportes de 404/401 con algunas cuentas. Decidido por Rafa añadirlo igual, registrado como `claude-design` y con aviso `unverifiedEndpoint` al generar. No tiene OAuth propio: entra con la sesión de Claude Code, así que Galeno lo registra y comprueba el estado sin abrir ningún navegador (`claude mcp login` responde que no hay nada que autorizar). Puede crear, editar y borrar archivos, así que de fábrica **pregunta** (el resto de escrituras internas van sin preguntar). Sin logo propio: un símbolo genérico hasta tener uno con licencia
- Email — **Gmail** (OAuth oficial de Google; mismo flujo que Drive)
- Transcripciones de reuniones — **directo por MCP oficial**: Fireflies (`api.fireflies.ai/mcp`), Granola (`mcp.granola.ai/mcp`), Fathom (`api.fathom.ai/mcp`, gratis en todos los planes). Google Meet: vía el MCP de Google Drive (las transcripciones de Gemini caen ahí)

**Escribe en (con aprobación humana para lo externo):**
- Notion y Jira — crear/actualizar tareas y docs
- Google Docs — escribir documentos
- Slack — enviar informes a canales
- Email — redactar y enviar (con aprobación)

**NO hace en v0.0.1:**
- Enviar por WhatsApp
- Garantizar la separación de contexto entre agentes. Se pueden crear varios agentes, uno por proyecto (§3b), pero salvo en WhatsApp la separación es por instrucción, no por estructura (ver §5)
- Trabajar por su cuenta sin aprobación humana para lo que sale: las tareas programadas entran con alcance acotado (decisión de Rafa, 5 oct 2026; ver §3b «Tareas programadas») y **ningún envío desatendido**: lo que vaya a otra persona queda como borrador hasta que alguien lo apruebe
- Generar config para otros agentes que no sean Claude Code

## 3. El flujo del wizard (pantallas)

> **Rediseño «Activación» (5 oct 2026, decidido por Rafa tras el demo de Aquiles).** El asistente se reordena para un usuario nada técnico; la referencia es `Galeno B1 Activación.dc.html` (Claude Design) en **estructura y textos**, con el estilo actual de Galeno (colores, tipografías, láminas, retrato, glifos, sonidos). Manda sobre la lista numerada de abajo donde se contradigan. El usuario ve **siete pasos** (el boceto traía seis: quitaba «Skills» al crear un agente, y Rafa la pidió de vuelta tras su prueba del 5 oct 2026):
>
> 0. **Antes del asistente, una sola vez** (`OnboardingView`, `Prefs.onboardingSeen`): tres pantallas de una frase —qué es, qué va a pasar («Tres pasos, unos diez minutos») y qué hay que tener a mano—, que se pueden saltar. El idioma arranca en el del Mac y se cambia ahí mismo, al pie; ya no hay pantalla de idioma y bienvenida. Solo en el asistente completo: «Nuevo agente» y «Gestionar» no las muestran.
> 1. **Rol** — «¿En qué trabajas?»: Producto, Marketing o Comercial (`AgentRole`). Decide tres cosas: **las skills** que trae el agente (las de los grupos del rol, `SkillCatalog.defaultSelection(for:)`; «Reportes» y «Reuniones» son comunes a los tres: producto 18, marketing 19, comercial 28), **el orden** en que se ofrecen y se conectan las herramientas (`AgentRole.toolOrder`) y **cómo se presenta** el agente en su `AGENTS.md`. El rol no se puede cambiar después desde «Gestionar» (por eso la pantalla no promete «se cambia después», como decía el diseño).
> 2. **Tu cuenta de Claude** — la detección de siempre (instalar, actualizar, iniciar sesión con un botón).
> 3. **Nombre** — solo el nombre, con su ex libris. Y, en la pantalla siguiente (mismo número de paso), **«Darle contexto a <agente>»** (`ContextStepView`; decisión de Rafa, 5 oct 2026: va **antes de las herramientas**, no solo desde la tarjeta del agente como en el boceto): opcional, una línea sobre el proyecto y archivos PDF, `.md` o `.txt` que se arrastran o se eligen. Sin nada escrito el botón dice «Saltar». El camino de copiar un mensaje a un chat de Claude y pegar la respuesta sigue, tras un enlace discreto. Darlo también después, desde la tarjeta del agente, sigue pendiente (fase 4).
> 4. **Herramientas** — una sola grilla en el orden del rol, con **las tres primeras marcadas**; las marcadas llevan su número, que es el orden en que se conectan. Lo que el usuario marque por su cuenta no se pisa si vuelve a cambiar de rol. Después, «Conectar» una por una (mismo paso para el usuario).
> 5. **Skills** — la misma pantalla de siempre, con las del rol ya marcadas. Lo que el usuario marque no se pierde por volver a pasar por el rol sin cambiarlo; si cambia de rol, llegan las del rol nuevo.
> 6. **Reglas.**
> 7. **Creación** — «Revisión», «Creando» y «Listo» comparten número.
>
> La cabecera dice «Paso N de 7» (6 en «Nuevo agente», 4 en «Gestionar») y, desde que el agente tiene nombre, lo muestra a la derecha; ya no hay estimación de minutos.
>
> **Abrir en la app de Claude tras reiniciarla:** el enlace solo se manda cuando la app **dejó de cargar** (`SystemAgentOpener.waitUntilClaudeSettles`: sus procesos casi sin usar el procesador dos segundos seguidos, y **mínimo 20 s desde que se lanzó**, tope 35 s; antes eran 3 s fijos y luego 4 s desde la ventana). Un enlace que llega antes pierde su carpeta y la app se queda con la última que usó, que puede no existir («Folder not found», prueba del 5 oct 2026), o **se rechaza y la conversación se abre sin la primera pregunta** (registro de la app del 6 oct 2026: «navigateTo loadURL rejected» 3 s antes de que terminara de arrancar; el procesador estaba quieto esperando a la red). Mientras tanto «Listo» dice que está abriendo, y después cómo repetirlo si no cayó en su carpeta (el segundo intento, con la app ya abierta, sí cae). **Slack, página de tokens:** justo después de iniciar sesión, Slack a veces pinta `api.slack.com/apps` **sin la sección de tokens** (visto en el registro de la prueba del 5 oct 2026: 37 s parado, con el aviso pidiendo un botón que no estaba, hasta que el usuario pulsó «Ir a la página de tokens»; la recarga la trajo y el resto tardó 2 s). Ahora, si la página lleva 5 s con sesión y sin controles, Galeno la vuelve a cargar sola, hasta dos veces, y nunca si el usuario ya está tocando la página (`SlackSignInModel.reloadDelay`). Además, el clic en «Generate Token» se repite si el diálogo no aparece y el botón se trae a la vista.
>
> **Las esperas no son una rueda sola** (pedido de Rafa tras la prueba de arranque limpio): mientras Galeno busca, instala o espera el inicio de sesión de Claude Code, se ven frases que se escriben solas, un trazo que va y viene y el tiempo transcurrido (`WaitingTicker`). Las frases **no fingen un progreso que Galeno no conoce** (no se lee la salida del instalador): dicen cosas ciertas pase lo que pase, y pasados 90 s reconocen la demora. **Vocabulario:** el agente se **crea**, no se «escribe» («Crear a Hera», «Creando a Hera»).
>
> **Construido (fase 1):** las tres pantallas previas, el rol, el nombre, «Darle contexto», la grilla por rol, la numeración y las esperas. **Pendiente, por fases:** (2) el paso de la cuenta de Claude con avance automático y la tira de conexión nueva (insignias, estado parcial de Google, cierre con resumen, «Empezar esta conexión de cero»); (3) reglas como interruptores, revisión en tres bloques, «Creando» en cuatro pasos y un «Listo» que al abrir vuelve al inicio; (4) desde el home, la hoja «Herramientas de <agente>» (conectar, reconectar, desconectar, cuenta compartida) y «Darle contexto».

1. **Idioma y bienvenida** — el usuario elige **español o inglés** (preseleccionado según el Mac). Define el idioma de todo el wizard y el que el motor inyecta en la config. Luego: qué es, qué va a configurar, cuánto tarda (~10-15 min según cuántas tools conecte).
2. **Claude Code** — comprueba que esté instalado, al día y con sesión; lo que falte lo hace Galeno con un botón (instalar, actualizar, iniciar sesión).
3. **Tu agente** — el usuario le pone nombre a *su* agente ("¿Cómo quieres llamarlo?"), rol (en v0.0.1 solo "Product Manager"), y **una línea que describe el proyecto** ("App de citas para la clínica X, lanzamos en noviembre"). Galeno es la app; el agente es del usuario. La descripción es deliberadamente corta: el agente la completa en su primera sesión (§3b).
4. **Elige tus herramientas** — una sola pantalla con la grilla de todas las tools disponibles (WhatsApp, Slack, Notion, Google Drive/Docs/Sheets, Jira, Google Calendar, Claude Design, Gmail, Fireflies, Granola, Fathom). **Google Meet no va en la grilla** (decisión de Rafa, 4 oct 2026): no tiene servidor y sus transcripciones se leen por Drive. El usuario marca **solo las que usa**. Esto define cuántos pasos tendrá el sub-wizard siguiente: si marca 4, son 4 conexiones; si marca 8, son 8. Al pie, un texto tipo "Vas a conectar 5 herramientas · ~8 min".

5. **Conecta una por una (sub-wizard dentro del wizard)** — patrón de onboarding tipo Cal AI / Duolingo. Es el paso más largo del producto, así que está diseñado para **mantener el enganche**:
   - **La tira de logos siempre visible** arriba, unidos por una línea punteada y apagados hasta que cada uno se conecta (entonces se encienden y se trazan su palomita). **Sin cuenta escrita** («3 de 5», «Google Docs · 2 de 3»): competiría con el «Paso 5 de 7» del asistente, que es el único progreso que se numera (6 oct 2026, petición de Rafa). La cuenta queda solo para VoiceOver.
   - **Una conexión por pantalla**, en orden. Cada pantalla: logo grande, una línea de qué va a poder hacer el agente con esa tool ("Leerá tus canales de Slack para hacerte seguimiento"), botón "Conectar" que lanza el OAuth (o el QR en WhatsApp, con su advertencia explícita, ver §4).
   - **Feedback inmediato al conectar:** animación corta de éxito (check que se dibuja, el logo "encendiéndose"; con trazo y opacidad, sin rebotes ni confeti de colores — ver `04-design-system.md` §8), texto tipo "¡Slack conectado! Encontré 12 canales". **Mostrar un dato real** de lo que se conectó (cuántos canales, cuántos grupos, cuántas reuniones) hace que el usuario sienta que el agente ya "ve" su mundo.
   - **Transición automática** a la siguiente conexión tras ~1.5 s, sin que el usuario tenga que dar "siguiente" (puede saltar con un botón discreto "Conectar después").
   - **Pantallas de dopamina intercaladas** cada 2-3 conexiones, para romper la sensación de proceso largo: una pantalla a pantalla completa, sin botones de OAuth, que celebra el avance y anticipa valor. Ejemplos:
     - Tras las 2 primeras: "Tu agente ya tiene memoria de tus reuniones y tu Slack. Esto es lo que va a poder hacer…" con 3 ejemplos concretos de comandos.
     - A mitad: "Ya vas por la mitad. La mayoría de los PMs recupera ~1 hora al día con esto."
     - Antes de la última: "Una más y tu agente queda listo."
   - **Si un OAuth falla**, no se rompe el flujo: mensaje claro, botón "Reintentar" y botón "Saltar por ahora" (la tool queda marcada para conectar después desde la app). El usuario nunca se queda atrapado.
   - **Al terminar todas:** pantalla de celebración grande ("¡Listo! Tu agente ve X canales, Y grupos, Z reuniones") que da paso al siguiente paso.

   **Principio de diseño:** el usuario siempre sabe dónde va, cada conexión le devuelve algo tangible, y nunca hay más de ~2 min sin una pequeña recompensa visual.

6. **Elige tus skills** — cards en una lista por grupos que se desplaza (rediseño del 5 oct 2026, archivo «Galeno B1 Skills» del proyecto de Claude Design; es la misma pantalla en el asistente y en «Gestionar»). El diseño traía dos formas de navegar y recomendaba pestañas; **Rafa eligió el scroll con rótulos fijos**:
   - **Las nuestras:** las 17 skills del perfil PM (§6.1) y las 5 de comercial (§6.3) como **cards** de tres columnas, en una sola lista. Cada grupo lleva su rótulo en versalitas con su «marcadas/total», que se queda fijo arriba mientras se desplazan sus cards. Cada card lleva su dibujo, el nombre, el comando y qué hace (dos líneas; el texto completo está en la vista previa). Arriba, junto al título, lo que vale para todo: «N de 17», «Todas» y «Ninguna». Todas marcadas por defecto; el usuario desmarca las que no quiere **para ese agente** (el catálogo es el mismo para todos sus agentes).
   - **Vista previa:** al pasar el cursor por una card (o con el foco del teclado) aparece «Vista previa», que abre una hoja **centrada** en la ventana (decisión de Rafa, 5 oct 2026; el diseño la hacía caer desde la barra de título). Dentro, una **demostración animada** de cómo se ve usar la skill (también pedida por Rafa): la pregunta se escribe sola, se envía, el agente —con el nombre del agente del usuario, sin la marca de Claude— «lee» sus fuentes y aparece el resultado **con la forma de lo que esa skill entrega** (un acta con secciones, un roadmap en tabla, un borrador para Slack). Es **ilustrativa**: los textos vienen del catálogo, no se llama a ningún modelo ni se gasta cuota, y la hoja lo dice siempre debajo («Ejemplo ilustrativo · no se ejecuta nada»), junto a «Ver de nuevo». Con «Menos movimiento» se muestra el resultado final sin animar. Debajo: cómo pedirla (el comando o una frase), qué necesita, dónde escribe y, si puede enviar algo a otras personas, que siempre pide aprobación. Desde ahí también se marca o desmarca.
   - **«Todavía no te sirve»:** a una skill que necesita una herramienta que el usuario no conectó se le apaga la card y dice qué falta («Falta: herramienta de reuniones»), pero se puede marcar.
   - **De otros autores:** las skills de la comunidad **ya no se muestran** (decisión de Rafa, 5 oct 2026): el foco son las nuestras y, cuando se revisen y se traigan con su licencia, las de Anthropic (`anthropics/knowledge-work-plugins`, Apache-2.0 por confirmar archivo por archivo), que van en el grupo de su rol con su crédito a la vista. **Traídas (5 oct 2026): diez de marketing**, en un grupo «Marketing»: siete de Anthropic (`campaign-plan`, `content-creation`, `email-sequence`, `brand-review`, `performance-report`, `seo-audit`, `competitive-brief`) y las tres de voz de marca de Tribe AI (`discover-brand`, `guideline-generation`, `brand-voice-enforcement`, licencia MIT, del mismo repositorio); ver §6.2. Las entradas de la comunidad siguen en `catalog.json` con `available: false` y sin tarjeta.
   - **Tus skills** (decisión de Rafa, 6 oct 2026): «Añadir skill…» va **en la cabecera, siempre a la vista** (junto a «N de 17 · Todas · Ninguna», con una línea debajo que dice qué se puede traer; al final de la lista nadie lo encontraba) y abre el selector de archivos; lo que se trae queda **al principio** de la lista, en un grupo «Tus skills»: una carpeta con `SKILL.md` o un archivo `.md` de su Mac. Quedan marcadas, se ven con lo que su `SKILL.md` dice (nombre y descripción del frontmatter, o el nombre de la carpeta y el primer párrafo), y con el cursor encima dicen «Quitar» en vez de «Vista previa». Solo archivos suyos: ver §6.3.
   - *("Trae la tuya" —pegar un link de GitHub o un catálogo de terceros— sigue fuera. Ver §5 y §6.3.)*

7. **Reglas** — el pacto: lo que nunca hace (enviar por WhatsApp), lo que siempre pregunta (todo envío externo) y lo que el usuario decide (escrituras dentro de sus herramientas).
8. **Revisión** — todo lo decidido en una página (herramientas, skills, reglas), con un «Cambiar» por bloque que vuelve a su paso. Nada se escribe hasta pulsar «Escribir a ⟨nombre⟩».
9. **Escribiendo** — el motor escribe la config. Los pasos se ven mientras ocurren (escribiendo reglas, conectando herramientas, creando skills, guardando) para que la espera también sea parte de la experiencia.
10. **Listo** — cómo usarlo, primeros comandos sugeridos, dónde está la config. Y la primera invitación a probarlo: "Pídele: resume lo que pasó esta semana en Slack". El usuario elige dónde abrir su agente: **en la app de Claude o en Terminal**. Desde aquí se llega al home (§3b).

> **Cambio del rediseño B1 (4 oct 2026, decidido por Rafa):** la pantalla «Elige qué leer» (el foco por herramienta) **sale del wizard**; en su lugar entra «Revisión». Sin ella, lo conectado se lee entero: el `AGENTS.md` dice «todo lo que la herramienta expone». El modelo (`SourceSelection`) y el código que lista fuentes (`SourcesFlow`, `SourceListing`) se conservan para ofrecer el foco más adelante, desde el home.

### Detalles de las pantallas 1–4 (decididos al construirlas, Fase 4)

La línea de cada pantalla de arriba no bastaba para construirlas. Esto es lo que se decidió; cualquier punto se puede cambiar.

| Tema | Decisión |
|---|---|
| Idioma | Selector segmentado en la pantalla 1, con cada idioma en su propio idioma ("Español" / "English"). Cambia **toda la app en caliente**, sin reiniciar. |
| Detectar `claude` | Una app abierta desde Finder hereda un PATH mínimo (sin Homebrew ni `~/.local/bin`). Se miran primero las rutas de los instaladores (`~/.local/bin/claude`, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.claude/local/claude`) y, si no está, un shell de login (`zsh -lic 'command -v claude'`, máx. 5 s) que cubre npm/nvm. Luego `claude --version` y `claude auth status` (solo se lee `loggedIn`; el correo no se guarda ni se muestra). |
| Versión mínima | **2.1.281** (`ClaudeCodeDetector.minimumVersion`; antes no había). ## 3b. Después del wizard

El wizard termina, pero el producto no. Un agente de Galeno es **una carpeta** (`~/Galeno/<agente>/`) con la config que el motor escribió; Claude Code la carga cuando se abre ahí. Todo lo que sigue sale de esa idea.

**El home.** Al abrir Galeno después del primer setup, el usuario ve la lista de sus agentes. Desde ahí puede:

| Acción | Qué hace |
|---|---|
| Abrir un agente | En la app de Claude o en Terminal, a elección del usuario, ya ubicado en la carpeta del agente |
| Crear otro agente | Un agente por proyecto. Lanza el **wizard corto** (abajo) |
| Gestionar la config | Cambiar fuentes, skills o reglas de un agente, sin repetir el wizard |
| Salud y mantenimiento | Conexiones caídas (con «Reconectar»), re-vincular WhatsApp (~cada 20 días), estado de la sincronización, carpetas borradas a mano, actualizar skills y la app (§4f) |

**Detalle del agente (implementado, 6 oct 2026; guiado por «Galeno B1 Agente» de Claude Design).** Un clic en la tarjeta del home, o en «Gestionar», abre el detalle del agente en vez del menú de tres opciones y del asistente: **todo lo configurado a la vista y editable en su sitio**. **Home v1 (implementado, 4 oct 2026, Fase 4b).** Al abrir Galeno con al menos un agente se ve el home: tarjetas de dos en dos (decisión de Rafa), con, por agente, su nombre, la descripción del proyecto, los logos de lo que lee hoy y «Lee N herramientas» (salen de las conexiones compartidas, así que una desconectada ya no aparece), y «Abrir». «Abrir» es un **botón partido** (como «Crear PR» de GitHub): lo principal abre donde se abrió la última vez (`Prefs.openTarget`, la app de Claude la primera vez) y a su lado una flecha despliega «Abrir en» [App de Claude | Terminal] con la elección marcada; elegir una abre y queda como la de ahí en adelante. Sin la app de Claude en el Mac no hay flecha: abre Terminal. En la app de Claude **vuelve a la última conversación de esa carpeta** (`claude://code/continue?session=…`, ver `AGENTS.md`) y, si no hay ninguna, abre una nueva; no lleva primera pregunta (el usuario ya conoce a su agente). Usa la misma lógica que «Listo» (`AgentOpenPolicy`): con conectores de la cuenta y Claude abierto desde antes, lo cierra y lo reabre en el agente, y la fila lo avisa antes de pulsar. **«Nuevo agente»** abre el **wizard corto** (implementado): reutiliza los mismos pasos del completo (`WizardState.Mode.short`), sin bienvenida ni detección, así que son 7 pasos —Tu agente · Tus herramientas · Skills · Reglas · Revisión · Escribiendo · Listo— más «Conectar» solo si el proyecto usa una herramienta que la instalación todavía no tiene conectada. Parte de `GalenoInstallation.startingPoint`: el idioma de la instalación y sus herramientas conectadas ya marcadas y con la etiqueta «Conectada» (se pueden desmarcar para este agente), con su `client_id`; «Conectar» recibe solo las nuevas. No guarda borrador. «Cancelar» en el primer paso vuelve al home sin crear nada; «Terminar» vuelve al home con el agente nuevo. Con la instalación ilegible el botón está deshabilitado. Si hay un borrador sin terminar, manda su pantalla «¿Seguimos?». Si `installation.json` no se puede leer, el home lo dice y deja reintentar: nunca se sobrescribe ni se vuelve al wizard en silencio. Una carpeta borrada a mano deja su tarjeta punteada y apagada, y su «Abrir» deshabilitado. **«Gestionar» (implementado):** un enlace en cada tarjeta abre las mismas pantallas del wizard con lo que el agente ya tiene (`WizardState.Mode.edit`): Tus herramientas → Conectar (solo lo que falta) → Skills → Reglas → Revisión → Escribiendo, y al guardar vuelve al home. No tiene bienvenida, nombre ni «Listo». Es también la forma de **recuperar una herramienta que se saltó**: vuelve a estar por conectar. La Revisión avisa antes de guardar: *«Al guardar, Galeno vuelve a escribir todos los archivos de <agente> a partir de lo que ves aquí. Lo que hayas editado a mano en ellos se pierde. Su carpeta memoria/ no se toca.»* Guardar regenera **la misma carpeta** (`AgentInstaller.install(existingAgentID:)`, no crea «Hera 2») y no escribe el material de contexto. Una herramienta que la instalación ya tiene conectada entra conectada, sin pasar por «Conectar». Sin carpeta (borrada a mano) el enlace queda deshabilitado: regenerar la crearía de nuevo en silencio, sin su memoria. **Si al guardar cambian las herramientas del agente** (decisión de Rafa, 4 oct 2026), Galeno lo anota, y la próxima vez que se abra ese agente en una app de Claude que ya estaba abierta desde antes, la cierra y la reabre en su conversación, avisándolo antes en la tarjeta: la conversación abierta arrancó con las herramientas viejas y no vería las nuevas (pasó con Jira). Guardar sin cambiar herramientas no reinicia nada. Sin verificar todavía que, tras reiniciar, la conversación retomada cargue los servidores nuevos. Desde el 6 oct 2026 «Gestionar» (y un clic en la tarjeta) abre el **detalle del agente** (arriba); *Renombrar…* y *Eliminar…* viven en su sección General, y el asistente de «Gestionar» queda para conectar herramientas nuevas.

**Renombrar** (decidido por Rafa, 4 oct 2026) cambia **solo el nombre**: la carpeta no se mueve —la app de Claude ata su historial a la ruta, y moverla rompería «volver a la conversación»—, `memoria/` no se toca, y Galeno vuelve a escribir los archivos del agente con el nombre nuevo (lo editado a mano se pierde, y el diálogo lo dice). La app de Slack ya creada conserva su nombre.

**Eliminar** (decidido por Rafa): manda **a la Papelera**, tras una confirmación que dice antes qué se va: la carpeta del agente con su `memoria/`, sus conversaciones de Claude Code (`~/.claude/projects/<carpeta>`) y sus conversaciones de la app de Claude (`claude-code-sessions/**/local_*.json` con ese `cwd`). Nada se borra para siempre. Solo se tocan rutas exactas de ese agente, y la carpeta solo si está dentro de `~/Galeno` y no es un enlace; no se toca `~/.claude.json` (ajustes de todos los proyectos), ni las conexiones compartidas, ni la sesión de WhatsApp, ni la app de Slack. Si la carpeta no se puede mandar a la Papelera, no se quita nada; si falla algo de lo de Claude, se avisa. Si era el último agente, se abre el wizard corto. Con la carpeta ya borrada, «Eliminar» solo lo quita de Galeno.

**Salud (implementado, 4 oct 2026, Fase 4b).** Un enlace «Salud» en la cabecera del home abre una vista a secciones (solo lee y diagnostica; las únicas acciones las pide el usuario):

- **Conexiones.** Cada herramienta conectada de la instalación con su estado: Conectada · Conectando · Falta autorizar · No responde · No está registrada · Sin saber. Los servidores propios salen de **`claude mcp list`** (una sola llamada); los **conectores de la cuenta de Claude** (Gmail, Drive, Docs, Sheets, Calendar) **no**: `mcp list` los da por conectados sin estarlo, así que se leen con el arranque de una sesión (`ClaudeSessionProbe`, §4e). Si `claude` no contesta se dice «Sin saber», nunca «Conectada». «Reconectar» vuelve a pasar por la autorización **de esa herramienta** (`claude mcp login`; el conector de la cuenta, `claude mcp login "claude.ai …"` o su página del directorio; Slack, en su ventana de Galeno). Galeno no pisa un servidor ajeno con el mismo nombre (dice que está ocupado), y a una herramienta con app OAuth propia cuya app ya no está registrada la manda a «Gestionar», porque rehacerla pide el secreto que solo existe mientras se crea la app.
- **WhatsApp** (solo si la instalación lo usa). Sesión (`galeno-whatsapp status --json`, bridge ≥ 0.3.0: `linked`, `number`, `linked_at` —la fecha que WhatsApp mismo pone al vincular el dispositivo—, `version`); si **`sync` corre** (`launchctl print gui/<uid>/com.galeno.whatsapp-bridge`); hace cuántos días se vinculó; la versión del puente. **Aviso de rotación:** desde los 18 días vinculado se avisa que WhatsApp *puede* cerrar la sesión hacia los ~20 (estimación de la guía, no un dato que WhatsApp publique; si el puente no pudo leer la fecha no se avisa). «Re-vincular» muestra la advertencia de WhatsApp de siempre —el mismo texto, sin tocarlo—, cierra la sesión anterior (`galeno-whatsapp unlink`, que detiene antes `sync` para que no se pisen) y muestra el **QR en pantalla**; al escanearlo reinstala `sync`. El historial ya sincronizado **no se borra**. Si cerrar la sesión falla, no se vincula nada nuevo. **Un segundo número (decisión de Rafa, 13 oct 2026, epic GAL-2; reabre la «separación de contexto entre agentes» solo para WhatsApp):** como máximo dos, y cada uno es una cuenta (`ConnectionID`) con su propio bridge (`--account <id>`: carpeta de estado, servicio de fondo `com.galeno.whatsapp-bridge.<id>`, bandeja, pausa y límites), su servidor (`whatsapp-<id>`) y su aceptación del envío. Se añade, re-vincula y desconecta desde el detalle del agente; Salud los lista; pausar y los topes valen para todos. Riesgo aceptado: más de una conexión no oficial desde la misma Mac puede hacer que WhatsApp restrinja un número.
- **Skills.** «Actualizar skills» es el punto de entrada (`SkillUpdating`); **el mecanismo llega con la Fase 5** (fuente remota versionada, §4f capa 3). Hasta entonces el botón sale deshabilitado con «se actualizarán desde aquí en una próxima versión».
- **Carpetas.** Si el usuario borró, movió o renombró la carpeta de un agente a mano, el home lo detecta (tarjeta punteada, «Abrir» y «Gestionar» deshabilitados) y ofrece, en la tarjeta y en Salud: **«Regenerar la carpeta»** (la vuelve a escribir en la misma ruta con la config guardada, tras un diálogo que dice que `memoria/` y lo editado a mano no vuelven; si la carpeta reapareció mientras tanto, no escribe nada) o **«Quitar el agente»** (el mismo diálogo de Eliminar, que con la carpeta ya ausente solo lo quita de Galeno y manda a la Papelera lo de Claude). Nunca se cae ni se borra nada en silencio.

**Pendiente de la 3b:** el mecanismo de «Actualizar skills» y la actualización de la app (Sparkle), Fase 5.

**Varios agentes, uno por proyecto.** Un PM con tres clientes crea tres agentes. Cada uno tiene su carpeta, su descripción, sus fuentes y su memoria. **Las conexiones de Galeno se hacen una sola vez y se comparten entre sus agentes** (con su nombre propio, `galeno-…`; las que el usuario tenga por su cuenta no entran aquí): el OAuth de cada herramienta lo guarda Claude Code por usuario, y WhatsApp es un solo dispositivo vinculado con una sola base local.

**Wizard corto** (del segundo agente en adelante): nombre, descripción del proyecto, qué leer y qué skills. No repite idioma, detección ni conexiones; solo pide conectar una herramienta si el proyecto usa una que todavía no está conectada. El motor arma el punto de partida del agente nuevo con las herramientas ya conectadas, con su `client_id`, y el idioma de la instalación (el del paso 1); qué lee de cada una queda por elegir.

**Qué se garantiza y qué no.** En ninguna herramienta la selección de fuentes es una barrera: es una instrucción en el `AGENTS.md`, que el agente obedece pero nada impide técnicamente. En WhatsApp, el bridge le da al agente todos los chats sincronizados. Se descartó filtrarlos por chat porque una lista fija obliga a reconfigurar cada vez que aparece un grupo nuevo; un grupo nuevo se le pide al agente en la conversación. Lo que sí se garantiza: leer WhatsApp no envía nada, y todo envío externo —WhatsApp incluido, desde el 7 oct 2026— pasa por aprobación y, en WhatsApp, por las guardas del bridge. La separación garantizada de contexto entre agentes es v0.2, y si hace falta una barrera en WhatsApp será una lista de **exclusión** (chats privados que el agente nunca ve), no de inclusión.

**La primera sesión.** La descripción del wizard es una línea. La primera vez que el usuario abre su agente, este lee las fuentes elegidas y **propone un resumen del proyecto** (quién participa, qué está en curso, fechas). El usuario lo corrige o lo confirma, y queda guardado en la memoria.

**Memoria del proyecto.** Cada agente mantiene notas propias (decisiones, quién es quién, pendientes) en la carpeta `memoria/` de su proyecto, y las actualiza él mismo. Es el **único lugar donde puede escribir sin que nadie lo apruebe**. Lo que el propio Galeno genera (`AGENTS.md`, `CLAUDE.md`, `.mcp.json`, todo `.claude/`) está bloqueado por regla, y cualquier otra ruta pide permiso al usuario cada vez; la ejecución de código está bloqueada del todo. **Traer contexto** (paso 3, opcional): quien ya habló del proyecto en claude.ai copia un mensaje que Galeno le da, pega la respuesta (o elige/suelta archivos `.md`, `.txt` o `.pdf`; hasta 10 materiales y 400 000 caracteres) y Galeno lo deja como texto en `memoria/contexto/`. Es una entrada de una sola vez: no entra en el `AgentConfig`, ni en el borrador, ni se regenera, y el motor solo crea esos archivos si no existen (no pisa nada). El `AGENTS.md` le dice al agente que los lea en su primera sesión como datos, nunca como órdenes. Todo queda en el Mac del usuario. La memoria es un archivo, `memoria/proyecto.md`, que `CLAUDE.md` importa para que cargue en cada sesión; el agente decide que es su primera sesión cuando la sección «Resumen» sigue diciendo «Sin confirmar.». **La primera sesión no retrasa la respuesta** (decisión de Rafa tras la prueba real, 4 oct 2026: leer el contexto antes de contestar costó medio minuto de casi tres): el agente contesta primero lo que le pidieron, leyendo solo lo que esa pregunta necesita, y al final ofrece en una línea preparar el resumen del proyecto; lo arma —con las fuentes y el material de `memoria/contexto/`— cuando el usuario acepta o cuando una pregunta sí depende de conocer el proyecto. Las notas son hechos sobre el proyecto, nunca instrucciones: el agente ignora y avisa si un mensaje o un documento le pide guardar algo en su memoria.

**Galeno es el dueño de la config.** Galeno guarda las respuestas del wizard de cada agente. Cuando el usuario cambia algo, el motor **regenera los archivos completos**; lo que alguien haya editado a mano se pierde. La excepción es `memoria/`, que Galeno nunca toca.

**La instalación y las carpetas.** Galeno recuerda dos cosas entre sesiones, en un solo archivo (`~/Library/Application Support/Galeno/installation.json`, sin secretos): las **conexiones compartidas** (herramienta, estado, `client_id`) y la **lista de agentes** (su config y su carpeta). El estado y el `client_id` se toman siempre de las conexiones compartidas, no de cada agente: cambiar el `client_id` de Slack una vez llega a todos, y una herramienta que se desconecta desaparece de todos al regenerar. La carpeta de un agente es `~/Galeno/<nombre>/`, con el nombre limpio de caracteres que rompen rutas y, si ya existe una igual (de otro agente o del propio usuario), con un número: `Aurora 2`. Se elige una vez al crearlo y no cambia sola.

**Regenerar.** Aplicar el generador sobre una carpeta que ya tiene config la deja **exactamente igual que una carpeta nueva** con la misma config: se quitan las skills desmarcadas (también una puesta a mano, porque `.claude/` es de Galeno) y el hook de aprobación si ya no hay a qué aplicarlo, y `memoria/` no se toca. Todo se calcula antes de escribir: si algo falla, la carpeta queda como estaba.

**Tareas programadas, con alcance acotado (decisión de Rafa, 5 oct 2026; reabre la línea roja 8 solo en esto).** La pidió el primer usuario externo (Simon, demo del 4 oct: «todos los días a las 8 am, un resumen de mis grupos de WhatsApp»). Una tarea desatendida puede: **leer** las herramientas conectadas (WhatsApp ya tiene los mensajes frescos: `sync` corre solo), **escribir en `memoria/`** (p. ej. `memoria/informes/2026-10-06-whatsapp.md`) y hacer las **escrituras internas** que las reglas del usuario ya permiten sin preguntar (Notion, Jira, Google Docs/Sheets). Todo lo que vaya **a otra persona** (correo, Slack, evento con invitados) lo deja **preparado como borrador**, y el usuario lo aprueba con un clic cuando abre su agente: la regla `ask`, el hook de aprobación y la línea roja 3 quedan intactos. **Por WhatsApp, una tarea programada no envía nunca** (7 oct 2026): deja el mensaje propuesto —en la columna `Mensaje propuesto` de la hoja o en `memoria/pendientes.md`, con el destinatario y el porqué— y en la primera sesión se ofrece uno por uno para aprobar. **Verificación hecha y construido (5 oct 2026, adelantado por decisión de Rafa).** La puerta pasó: (a) en una corrida sin terminal (`claude -p`) una herramienta bajo `ask` queda **denegada** —probado de primera mano en la carpeta de un agente real: el archivo no se creó y el agente recibió «no te han concedido el permiso»—; (b) en las **tareas programadas de la app de Claude** (el mecanismo elegido: locales, sobreviven reinicios, corren mientras la app esté abierta) una regla `ask` deja la corrida **esperando la aprobación** en la barra lateral, documentado en `code.claude.com/docs` («desktop scheduled tasks»); y (c) no existe modo documentado que se salte un `ask`. Las de la terminal (`CronCreate`) existen pero viven atadas a su sesión y caducan a los ~7 días. Lo construido: la sección «Tareas programadas» del `AGENTS.md` generado (programar siempre con permiso del usuario, nunca un modo que salte aprobaciones, el resultado a `memoria/informes/`, lo que necesite aprobación a borrador o a `memoria/pendientes.md`, y contarlo en la primera sesión siguiente); **los borradores de Gmail (`create_draft`, `update_draft`) pasan a `allow`** (`MCPServerDefinition.draftTools`) con su propio hook de paso libre en la app de Claude —la única excepción a «el paso libre es solo de lecturas»: un borrador queda en el buzón del propio usuario y no le llega a nadie; `delete_draft` y todo lo demás siguen preguntando—; y las tres skills que lo piden (`/tareas-recurrentes`, `daily-briefing`, `weekly-wrap`) dicen cómo programarse. Pendiente de probar a mano: una tarea real en la app de Claude de punta a punta. Dos avisos que el agente da al programar: la tarea corre solo con la app de Claude abierta, y la carpeta tiene que estar confiada (se acepta al abrir el agente la primera vez). El envío desatendido de verdad —sin nadie que apruebe— sigue fuera: es la cola de aprobaciones de v0.2 (§5).

## 4. WhatsApp — reglas de producto (innegociables)

**Cambio del 7 oct 2026 (decisión de Rafa, `docs/09-plan-simon-envio-y-prospeccion.md`):** WhatsApp pasa de solo lectura a **lectura libre y envío con aprobación**. Lo pidió el flujo de Simon (prospección desde una hoja y seguimientos diarios): el primer contacto sale por WhatsApp o correo, y el `wa.me` de `/prospeccion` se queda como respaldo. Hasta la 0.3.0 del bridge no existe código de envío; desde la 0.4.0 existe **uno solo**, con estas reglas.

- **Un solo envío: `send_message`.** Texto, a **una** persona o a **un** grupo en el que el usuario ya está. Nunca a listas de difusión, estados ni canales; nunca adjuntos, audios ni stickers. `send_file` y `send_audio_message` siguen eliminados.
- **Grupos, con el nombre a la vista (decisión de Rafa, 7 oct 2026).** El plan original no enviaba a grupos; Rafa lo pidió ese mismo día. Solo valen los grupos que ya están entre los chats sincronizados. Como al aprobar el usuario ve lo que pidió el agente, y de un grupo eso es un identificador que no dice nada, `send_message` exige el nombre del grupo y el bridge lo rechaza si no coincide con el guardado: lo que el usuario lee al aprobar es el grupo al que de verdad va el mensaje. Tienen su propio tope diario (10, techo 20) y además cuentan para el total.
- **Siempre con aprobación.** `send_message` va en `ask` y lo cubre el hook de aprobación, como Slack y Gmail. Una tarea programada **no envía**: deja el mensaje propuesto y el usuario lo aprueba en su primera sesión. Los subagentes nunca reciben la herramienta.
- **Las guardas viven en el bridge, no en el prompt** (`docs/09` §4.4): topes diarios (40 en total, 15 chats nuevos) con un techo fijo en el código que el usuario puede bajar y nunca subir; espaciado aleatorio de 45–120 s; el mismo texto a más de 3 chats se rechaza; 1.000 caracteres como mucho; y una pausa total (`send-paused`), que además cancela lo que estaba en cola.
- **Sin guarda de horario ni de festivos (decisión de Rafa, 7 oct 2026).** El plan original solo enviaba de lunes a viernes de 8 a 19 y sábados de 8 a 13. Rafa decidió que Galeno no discrimine por hora ni por día: lo decide el usuario, que aprueba cada mensaje. **A cambio se le avisa**: el agente lo dice antes de proponer un mensaje de noche, en domingo o en festivo, y la advertencia de la app lo menciona. La Ley 2300 de 2023 limita el horario de los contactos comerciales en Colombia; Rafa lo valida con un abogado antes de vender a más usuarios.
- **No se activa solo en quien ya tenía Galeno (decisión de Rafa, 7 oct 2026).** Quien vinculó WhatsApp cuando Galeno solo leía aceptó una advertencia que decía «solo lectura». Al actualizar, su agente **sigue solo leyendo**: el motor escribe el envío únicamente si la conexión lleva `sendingAccepted` (`ToolConnection`, tomado de la conexión compartida). El home se lo ofrece una vez («WhatsApp ahora también puede enviar mensajes, solo con tu aprobación») y **Salud** tiene «Activar envíos…»: enseña la advertencia nueva y, al aceptar, deja el bridge al día, reinicia `sync` y vuelve a escribir los agentes que usan WhatsApp (`memoria/` no se toca; lo editado a mano en ellos se pierde, y la pantalla lo dice). Vincular o re-vincular con la advertencia nueva también cuenta como aceptarlo.
- **Lo que se ve en Salud.** «Enviados hoy: N de 40 · nuevos M de 15 · grupos G de 10» (lo enviado y lo que está en cola cuentan), lo que hay en cola, «Pausar envíos» y «Límites», donde los topes se pueden bajar y nunca subir por encima del techo del bridge.
- **Un mensaje aprobado no espera para siempre (decisión de Rafa, 7 oct 2026).** Si no pudo salir porque el Mac estaba apagado o sin conexión, espera **24 horas** y después caduca (`failed`, diciendo por qué): no sale días más tarde, cuando el usuario quizá ya escribió a mano.
- **Por una bandeja de salida, no por otra conexión.** `serve` (el que lanza Claude Code) no se conecta a WhatsApp: escribe en `outbox` (SQLite) y `sync`, la única conexión viva, despacha. Dos conexiones del mismo dispositivo es justo lo que se evitó.
- **La herramienta solo aparece si la config la pide.** `serve` a secas ofrece las 9 lecturas; `send_message` solo existe con `serve --with-send`, que el motor escribe en el `.mcp.json` junto con la regla `ask` y el hook de aprobación. La config generada antes del envío permitía el servidor entero (`mcp__whatsapp__*`): sin esta compuerta, un agente creado antes y un bridge actualizado enviarían sin preguntar. Un agente viejo sigue siendo de solo lectura hasta que se regenera.
- **El agente ve todos los chats sincronizados, incluidos los personales.** No hay filtro por chat (ver §3b). La app tiene que decirlo con claridad en la pantalla "elige qué leer": lo que el usuario elige es en qué se enfoca el agente, no lo que puede leer.
- **Transparencia total.** La advertencia dice, palabra por palabra (versión del 7 oct 2026, con el envío, los grupos y sin límite de horario; **es una propuesta hasta que Rafa apruebe el texto exacto**, y la traducción al inglés también la aprueba él): "Esto se conecta como un dispositivo vinculado usando el protocolo de WhatsApp Web, de forma no oficial. Tu agente puede leer tus chats y enviar mensajes, a una persona o a un grupo, solo cuando tú apruebes cada uno. WhatsApp no permite oficialmente este tipo de conexión: existe un riesgo real de que restrinja o bloquee tu número, sobre todo si escribes a muchas personas que no te tienen guardado. Galeno pone límites diarios para reducirlo, pero no lo elimina. No limita el día ni la hora: cuándo escribir lo decides tú. Todo corre en tu computador; nada sale a servidores nuestros. Tú decides si continuar." Es el mismo texto al vincular, al re-vincular y en «Activar envíos» de Salud; la app lo toma de aquí y una prueba compara los dos (`testTheWhatsAppWarningIsTheOneInTheSpecVerbatim`). Nunca dice que es «seguro» ni «oficial» (línea roja 9).
- **Base técnica (decidida):** fork de **`lharries/whatsapp-mcp`** — **MIT verificada**, 5.9k estrellas, 1.2k forks: el estándar del espacio. Dos componentes: puente en Go (`whatsmeow`, QR, SQLite) + servidor MCP en Python. Trae **12 herramientas, 3 de envío** (`send_message`, `send_file`, `send_audio_message`) → **se eliminan**. Quedan las de lectura: contactos, chats, mensajes, contexto, descarga de media. El propio autor advierte la trifecta letal; quitar el envío es la mitigación.
  - **Decisión de empaquetado (cerrada):** reescribir el servidor MCP de Python a **Go**, dentro del mismo binario del puente → **un solo ejecutable Go, sin Python**, empaquetado en la .app. Cero dependencias para el usuario. Por qué Go y no Swift: `whatsmeow` (el puente, la parte difícil) solo existe en Go; el MCP va junto al puente para que el componente de WhatsApp sea un binario autocontenido que Claude Code lanza como cualquier MCP por stdio. Nunca empaquetar Python.
  - Operativo para la UX: re-autenticación cada ~20 días (aviso de "re-vincular"); la carga inicial del historial puede tardar minutos (barra de "sincronizando" en la primera conexión).
  - **Alternativas en TypeScript, evaluadas y descartadas** por la decisión de Go: `exomind-tmi/whatsapp-mcp` (Baileys; buen diseño de daemon único + shims) e `ionutsss1/whatsapp-mcp`. Más maduros que joaohts, pero obligarían a empaquetar Node.
  - **`joaohts/whatsapp-mcp` (MIT) solo como referencia de UX**, no de código: 0 estrellas, 0 forks, pre-alpha, un solo autor. Tomar sus ideas (QR en pantalla, toggles por herramienta, variante DMG), no heredar código sin probar.
- **Re-vinculación:** el protocolo rota la sesión ~cada 20 días; la app debe avisar y ofrecer re-escanear.
- **Por qué los topes y la aprobación, y no solo lectura:** el riesgo de ban se dispara con el envío automatizado y en frío. Que cada mensaje lo apruebe una persona, con topes y espaciado, y sin difusiones, lo acerca a lo que hace un humano con WhatsApp Web; no lo elimina, y la advertencia lo dice. La recomendación a los usuarios es que la prospección en frío vaya **primero por correo** cuando haya correo.

## 4c. Arquitectura de Galeno.app (Swift)

```
Galeno.app  (Swift / SwiftUI)
  ├── Wizard y UX           → SwiftUI nativo (animaciones de dopamina, QR en pantalla)
  ├── Generador de config   → escribe AGENTS.md, .claude/settings.json, .mcp.json, skills, hooks  (FileManager)
  ├── WhatsApp              → lanza y supervisa un binario Go empaquetado (puente + MCP: lectura y send_message)  (Process)
  │                            · launchd para que arranque solo al iniciar sesión
  └── Demás MCP (hospedados) → corre `claude mcp add --transport http …` + abre el OAuth  (Process)
                               Notion · Slack · Gmail · Drive · Jira · Fireflies · Granola · Fathom
```

**Stack final:** Swift (app) + un binario Go (WhatsApp). Nada de Python, Node, Rust ni contenedor web. Los MCP hospedados no se empaquetan: viven en los servidores de cada proveedor y se conectan por OAuth.

**Por qué funciona bien en Swift:** `Process` lanza y supervisa binarios; `FileManager` escribe la config; SwiftUI hace el wizard fluido y nativo. Es la arquitectura natural para un orquestador de procesos locales.

## 4b. Transcripción de reuniones — la integración más limpia del stack

A diferencia de WhatsApp, aquí **todo es oficial y sin riesgo**: los tres proveedores principales hospedan su propio MCP con OAuth.

| Herramienta | MCP | Notas para el producto |
|---|---|---|
| Fireflies | Oficial, en el directorio de conectores de Claude | El más maduro. Transcripciones, resúmenes, action items |
| Granola | Oficial (reciente) | No guarda en nube. **Verificar**: una fuente dice que borra transcripciones a las ~72 h; si es así, el agente debe sincronizar pronto |
| Fathom | Oficial, 12 herramientas, todas de solo lectura (vistas en cuenta real, 4 oct 2026; van a `allow` por nombre y una nueva cae en el hook) | **Gratis en todos los planes.** Límite: la búsqueda lee títulos/resúmenes, no transcripciones; la transcripción completa se pide por ID |
| Google Meet | Sin MCP propio | Las transcripciones de Gemini caen en Drive → se leen con el MCP de Google Drive que ya está en el stack |

**Decisión de diseño:** las transcripciones se leen **directo de la fuente**, no vía export a Notion. Menos fricción (un OAuth y listo) y más confiable (nada reverse-engineered).

**Guardrail que se hereda a plantillas futuras:** la plantilla de salud debe advertir que nunca se transcriben consultas clínicas con pacientes.

## 4d. Internacionalización (español e inglés)

El modelo es multilingüe: un usuario hispanohablante obtiene la misma calidad que uno anglohablante. Las decisiones de i18n son de producto, no de capacidad.

| Capa | Decisión |
|---|---|
| **Wizard (la app)** | Se traduce: i18n nativa de Swift (String Catalog, `Localizable.xcstrings`), español e inglés. El usuario elige al inicio; preseleccionado según el idioma del Mac, y el cambio es en caliente (`\.locale`). Los textos de dopamina se escriben **nativamente en cada idioma**, no como traducción literal: "¡Vas por la mitad!" tiene que sonar a alguien que te habla. |
| **AGENTS.md y config generada** | El motor los genera en el idioma elegido, e inyecta la instrucción explícita: *"responde y genera todos los documentos en [idioma]"*. Esto evita que el agente devuelva un PRD en inglés porque el ticket de Jira estaba en inglés. |
| **Skills nuestras** | Se escriben **en inglés** (estándar del ecosistema, una sola fuente que mantener), con la instrucción de idioma arriba. Una skill en inglés funciona para un usuario en español: el agente lee la instrucción y responde en la lengua del usuario. |
| **Skills curadas** | Las que se traen (hoy, las de Anthropic) se **adaptan**: llevan la misma instrucción de idioma que las nuestras, primera línea tras el frontmatter. |

**Nota de diseño:** las fuentes del PM suelen estar mezcladas (WhatsApp en español, Jira en inglés, docs en inglés). El agente lee todo sin problema; lo que fija el idioma del **output** es la instrucción explícita en la config, no el idioma de la fuente.

## 4e. Slack y Google Workspace/Gmail — la app OAuth es del cliente, nunca de Galeno

Investigando los MCP reales de Slack, Notion, Google Workspace y Atlassian (oct 2026) se encontró que no todos son "solo OAuth":

- **Notion y Jira** registran el cliente al vuelo (*dynamic client registration*): nadie crea nada de antemano. Endpoints confirmados: `mcp.notion.com/mcp` y `mcp.atlassian.com/v2/mcp` (la `v1/sse` que se había anotado antes se apaga el 30 de junio de 2026).
- **Jira, probado con cuenta real (4 oct 2026).** El servidor de Atlassian (Rovo MCP v2) trae 21 herramientas y no es solo Jira: con la misma cuenta lee Confluence, Loom y el grafo de Atlassian. Permisos (`MCPServerCatalog.jira…Tools`): las 12 de lectura van sin preguntar (incluidas `discover`, que busca en el catálogo de herramientas diferidas, y `executeRead`, que ejecuta las que el servidor marca como lectura); las 7 que crean o editan (tickets, comentarios, transiciones, páginas de Confluence) siguen la regla de Jira del paso «Reglas»; y **dos preguntan siempre**, diga lo que diga la regla: `executeDestructive` (borra para siempre) y `executeWrite` (ejecuta cualquier herramienta diferida de escritura, entre ellas compartir un video de Loom, abrir un enlace público de Confluence o cambiar permisos). Lo que Atlassian añada después cae en el hook. Los subagentes reciben las lecturas y las siete escrituras, nunca esas dos.
- **Slack y Google Workspace/Gmail exigen una app registrada con el proveedor** antes de que cualquier cliente pueda conectarlos. Eso no es un token del usuario — es una credencial del fabricante del software.

**Decisión: esa app la trae el propio cliente, nunca Galeno.** Coherente con "los secretos del usuario nunca tocan tu infraestructura", un paso más allá: ni el `client_id` es de Galeno. La alternativa —Galeno registra una sola app para todos los clientes— exigiría pasar la revisión del Marketplace de Slack y la verificación de scopes sensibles de Google (semanas, y una app compartida que mantener). Trayendo cada cliente la suya, ninguna de las dos hace falta.

**Cómo se resuelve cada una, sin pedirle al usuario que configure nada a mano:**

| | Slack | Google Workspace / Gmail |
|---|---|---|
| **Mecanismo** | **Por API, sin pantallas.** `apps.manifest.create` recibe el manifiesto y devuelve el `client_id`/`client_secret` directamente en la respuesta (confirmado contra la referencia oficial del método) — Galeno nunca muestra una pantalla de Slack ni pide copiar nada | No existe un atajo equivalente (Google apagó en marzo de 2026 la única API parecida que existía, para un caso de uso distinto). Se resuelve con **automatización real de navegador**: la app maneja los clics de crear el proyecto y la credencial en la consola de Google, parando solo para que el usuario inicie sesión |
| **El único paso que Slack no deja evitar del todo** | Generar el primer "token de configuración de apps" exige entrar a `api.slack.com/apps` → "Your App Configuration Tokens" → "Generate Token": Slack mismo dice que no hay forma programática de arrancar ese primer token. **Decisión: lo hace la automatización de navegador de Galeno**, igual que con Google —parando solo para que el usuario inicie sesión en Slack—, no el usuario a mano. Es un paso único **por workspace**, no por conexión ni por app: de ahí en adelante `SlackAppProvisioner.rotate(refreshToken:)` lo renueva solo, sin volver a tocar el navegador | Crear el proyecto y la credencial en la consola de Google, de principio a fin |
| **Dónde vive** | `GalenoCore`: `SlackManifestRenderer` (el manifiesto) + `SlackAppProvisioner` (la llamada a la API). La automatización que consigue el primer token de configuración es de `GalenoApp`, Fase 4 — un solo clic en una sola pantalla ("Generate Token"), mucho más acotado que el flujo de Google | GalenoApp, Fase 4. Varias pantallas (proyecto, consentimiento, credencial) |
| **El riesgo que se acepta** | Que Slack detecte la sesión como automatizada en una acción sensible (genera un token con permiso para crear apps en el workspace), y que la interfaz de esa pantalla cambie. Menor que el de Google: es un solo botón, no un flujo de varias pantallas con muchos campos | Frágil ante cambios de la consola; riesgo real de que Google detecte la sesión como automatizada en una pantalla sensible |
| **Qué guarda Galeno** | El `client_id` (texto plano: no es secreto), en `ToolConnection.oauthClientID`. El `client_secret` **pasa por `GalenoApp` en memoria, una sola vez**, directo de la respuesta de Slack a `claude mcp add --client-secret` (que Claude Code guarda en el keychain del sistema): nunca se escribe a disco, nunca se registra, nunca entra a `AgentConfig` ni a ningún archivo generado | Solo `client_id` |

**Sobre el `client_secret` de Slack:** es la única vez que algo que no es del propio usuario pasa, de paso, por el software de Galeno. Sigue siendo cierto que "los secretos nunca tocan infraestructura propia" —nada de esto sale de la máquina del usuario, ni se envía a ningún servidor de Galeno—, pero es una matización real que vale la pena tener presente al construir `GalenoApp`: ese valor se recibe, se entrega de inmediato al almacenamiento seguro de Claude Code, y se descarta. Nunca se loggea, nunca se persiste.

**Slack, además, solo soporta token de usuario.** Confirmado contra la documentación oficial: sus endpoints de autorización son específicamente para tokens de usuario (`oauth/v2_user/authorize`), y su tabla de scopes documentada es toda "user token". **Consecuencia:** todo lo que el agente haga en Slack aparece con el nombre y la foto de quien aprobó la conexión — no existe una identidad de bot separada dentro de esta integración, y construir una exigiría abandonar el MCP oficial de Slack por una integración propia. Para v0.0.1 se acepta esto tal cual: es, de hecho, un resultado natural y no un compromiso.

Los scopes que v0.0.1 pide a la app de Slack del cliente (verificados contra la tabla oficial, solo lo que usa el producto): `channels:read`, `groups:read` (listar canales), `channels:history`, `groups:history` (leer historial), `search:read.public`, `search:read.private` (buscar), `chat:write` (enviar, con aprobación). Los scopes de Google quedan pendientes de verificar cuando se diseñe la automatización de Fase 4.

**Google va por los conectores de la cuenta de Claude (decisión de Rafa, 4 oct 2026).** Gmail (`gmail-gmailmcp`), Google Drive (`google-drive-drivemcp`), Google Docs (`google-docs-docsmcp`), Google Sheets (`google-sheets-sheetsmcp`) y Google Calendar (`google-calendar-calendarmcp`) son conectores del directorio de Claude que usan los servidores oficiales de Google con la app OAuth de Anthropic. Claude Code los trae solos cuando el usuario entra con su cuenta de Claude, y sus herramientas se llaman `mcp__claude_ai_<Nombre>__…` (visto con Google Drive). No se registran ni van en `.mcp.json`. El token de Google lo guarda Anthropic, no Galeno ni el cliente. Google Slides existe en el directorio y no se usa.

**Los cinco se vieron en una cuenta real (4 oct 2026)** y el catálogo lleva sus herramientas exactas: Gmail 30 (6 leen; `send_message`, `reply` y `forward` envían, y las otras 21 cambian el buzón: todas piden aprobación), Calendar 9, Drive 11, Docs 2, Sheets 9. Ya no sale ningún aviso de endpoint sin verificar por Google.

**Por qué no se registra la URL del servidor de Google en `.mcp.json`** (se probó el 4 oct 2026, idea de Rafa). Cada conector tiene detrás un servidor de Google (`https://gmailmcp.googleapis.com/mcp/v1`, `drivemcp`, `docsmcp`, `sheetsmcp`, `calendarmcp`) que responde y lista sus herramientas sin credenciales, pero cada llamada exige un token de `accounts.google.com`, y Google **no ofrece registro dinámico de clientes** (su metadato no trae `registration_endpoint`). Registrarla directo pide un `client_id` y un `client_secret` de una app de Google Cloud: la del cliente (descartada arriba) o una de Galeno, que exigiría la verificación de Google para permisos restringidos (Gmail: auditoría de seguridad anual) y el Developer Preview. El conector de claude.ai funciona porque usa la app de Anthropic. Queda como opción de producto para más adelante, no para v0.0.1.

**Conectores y la app de Claude (escritorio).** El objetivo (Rafa, 4 oct 2026): conectar Drive, correo y calendario en Galeno, abrir el agente en la app de Claude, preguntar y que responda bien. Tres diferencias con Terminal, vistas ese día:

1. **Se encienden por conversación.** En Terminal los conectores de la cuenta llegan encendidos; en la app, cada conversación los trae encendidos o apagados (menú + → Conectores; la última elección queda de fábrica para las nuevas). No hay ajuste de proyecto ni parámetro de `claude://code/new` que los encienda (solo existen `disableClaudeAiConnectors` y `deniedMcpServers`, para apagarlos). El `AGENTS.md` generado lleva la sección «Si una herramienta conectada no aparece»: el agente mira el estado (`mcp__ccd_connectors__session_connectors_status`), enciende **solo los conectores que Galeno conectó** (`set_session_connector_enabled`, que el usuario aprueba) y pide repetir la pregunta, porque las herramientas llegan en el mensaje siguiente.
2. **La app carga la lista de conectores al arrancar y no la actualiza** (confirmado el 4 oct 2026). Un conector autorizado con la app ya abierta no aparece en ella —ni en el menú + → Conectores ni en su directorio, que lo muestra con «+»— hasta cerrarla (Cmd+Q) y abrirla de nuevo; tras reiniciar, los cinco de Google aparecieron y **encendidos**. Terminal no tiene este problema: cada sesión los lee al empezar. Lo mismo al revés: uno desconectado sigue saliendo como conectado hasta reiniciar. **Decisión de Rafa (4 oct 2026):** si el agente usa conectores y la app de Claude lleva abierta desde antes de que el agente existiera, «Abrir en la app de Claude» la **cierra y la vuelve a abrir en el agente** (`restartClaudeAppAndOpen`). Se le pide salir como con Cmd+Q, nunca se la mata; si no sale en 15 s (un aviso suyo, una tarea a medias), **no se abre el agente** en esa app —no vería sus conectores— y la pantalla lo dice: «Claude no se cerró… ciérralo con Cmd+Q y pulsa Abrir otra vez» (`AgentOpenOutcome.claudeDidNotQuit`). La nota bajo los botones lo avisa antes de pulsar. Con Claude cerrado, o abierto después, no se reinicia nada.
3. **Las herramientas se llaman distinto.** En Terminal, `mcp__claude_ai_<Nombre>__<herramienta>`; en la app, `mcp__<uuid>__<herramienta>`, con un identificador por usuario que Galeno no conoce. Las reglas de permiso no admiten comodín en el servidor (probado), así que en la app no coincide ninguna. Lo cubren dos hooks, cuyo `matcher` sí es una expresión regular y decide **por el nombre de la herramienta**: `require-external-approval.sh` pide aprobación para todo lo que no sea una lectura o una escritura conocida (enviar un correo, crear un evento, compartir, y cualquier herramienta nueva), y `allow-connector-reads.sh` deja pasar **solo las lecturas** conocidas. Las escrituras que en Terminal siguen la regla del paso 8 (Docs, Sheets), en la app preguntan: decidir una escritura por nombre podría aprobar la de otro conector que se llame igual. Límite conocido: los subagentes reciben las herramientas por su nombre de Terminal, así que en la app no leen Google; lo lee el agente principal.

**Leer bien el estado de un conector que ya estaba conectado** (demo de Felipe, 4 oct 2026). Felipe ya tenía Drive, Docs, Sheets y Gmail conectados en Claude Code antes de usar Galeno. El paso 5 abrió la página del conector —que decía «Connected»— y se quedó girando; hubo que saltarlo y el agente se escribió sin Google. El estado se lee del arranque de una sesión (`ClaudeSessionProbe`), y ese arranque engañaba de dos formas, las dos reproducidas:

- **La lista de conectores de la cuenta no había llegado.** A veces Claude Code da su estado inicial (en 1–2 s) antes de recibir de claude.ai la lista de conectores: no trae ninguno. Galeno lo leía como «no está en la cuenta» y abría la página del directorio. Ahora, si el arranque no trae **ningún** `claude.ai …`, se vuelve a mirar (hasta 3 veces) antes de creerlo.
- **La caché de descubrimiento.** Con ella (se activa por cuenta, en despliegue gradual), un servidor remoto que ya se usó no se conecta al arrancar y sale `pending` en todas las sesiones («connects on first use»). Galeno esperaba un `connected` que nunca llegaba. Ahora el sondeo arranca con `MCP_DISCOVERY_CACHE=0`, `MCP_CONNECTION_NONBLOCKING=0` y `MCP_CONNECT_TIMEOUT_MS=8000` (variables documentadas), así que el estado es el real. `pending` nunca significa «falta autorizar», que es `needs-auth`; **y tampoco «conectado»** (ver abajo, demo de Aquiles).

**Solo cuenta un «conectado» de verdad** (demo de Aquiles, 5 oct 2026). Aquiles abrió la página de Google Calendar, pulsó «Connect» y se quedó en el selector de cuentas; Galeno lo marcó conectado. Era la regla añadida tras el demo de Felipe: tres lecturas `pending` seguidas contaban como conectado. Ahora el paso del tiempo no marca nada, ni antes ni después de abrir el navegador, ni en el asistente ni en «Reconectar» de Salud:

- Un conector `pending` (o que no respondió) se mira unas veces más (`Timing.connectorPendingLooks`). Si sigue así, se abre su página en Claude, que dice su estado real, y se espera.
- Durante la espera hay dos salidas a la vista: **«Ya lo conecté, comprobar»** (`ConnectFlow.confirmConnector`: mira ya, con un arranque nuevo) y «Abrir la página otra vez». Si al comprobar el conector sale `connected`, o `pending` (es el usuario quien lo afirma), se da por conectado; si sale `needs-auth` o no está en la cuenta, se dice «Todavía no aparece conectado» y la espera sigue. Es la salida del cuelgue del demo de Felipe sin que Galeno adivine.
- Esto se apoya en la versión mínima de Claude Code (2.1.281, §3): por debajo, el sondeo veía `pending` casi siempre.

Además, los conectores que se miran seguidos (Drive, Docs y Sheets) comparten un mismo arranque (`SessionStatusCache`, 6 s): antes eran tres arranques de 5–15 s para leer lo mismo. **Sigue pendiente:** un agente al que se le saltó una herramienta no tiene cómo recuperarla (falta «Gestionar la config»); hoy la salida es crear otro agente con «Nuevo agente».

**La app de Claude se abre y se espera antes de mandarle el enlace** (4 oct 2026, agente «Aloha»). Tras crear a «Aloha», Galeno reinició Claude y le mandó el enlace con la carpeta de «Aloha»; el registro de la app muestra que arrancó a las 21:59:04 y abrió la sesión en la carpeta de **«Jarvi»** (la última que había usado), y que «Aloha» nunca aparece. La primera pregunta de «Aloha» quedó en el historial de «Jarvi» y, como esa carpeta no tiene las reglas de Google, la app pidió permiso para leer el calendario. Es decir: los agentes **sí** son independientes (carpeta, reglas, memoria y conversaciones propias); la conversación cayó en la carpeta equivocada. Causa probable (el registro no la prueba): un enlace que llega mientras la app carga puede perder su carpeta. Ahora, si hay que arrancar Claude, `SystemAgentOpener` lo abre, espera a que tenga ventana y a que termine de cargar (3 s más) y **solo entonces** manda el enlace; con Claude ya abierto no cambia nada. Vale para el reinicio, para «Listo» y para el home (`AgentOpening.prepareClaudeApp`). Sin verificar con la app real.

**Los comandos de los hooks van entre comillas** (`"${CLAUDE_PROJECT_DIR}/.claude/hooks/…"`). La carpeta de un agente puede llevar espacios; sin comillas el hook falla sin bloquear (`/bin/sh: …: is a directory`) y nadie pide aprobación ni deja pasar las lecturas. Pasó en la prueba del 4 oct 2026 con el agente «TESTING 2»: leer el calendario pidió permiso. Un test corre los dos hooks desde una carpeta con espacio.

**Galeno vuelve al frente al terminar cada conector** que pasó por el navegador (decisión de Rafa, 4 oct 2026), no una sola vez al final: con Drive, Docs y Sheets seguidos se ve que uno quedó antes de que se abra el siguiente (pausa de 1,2 s).

**Los demás conectores de la cuenta** (los que el usuario ya tenía: Lovable, PostHog…) se heredan pero no se encienden (decisión de Rafa, 4 oct 2026): no se niegan con `deniedMcpServers`, el agente solo enciende los suyos, y en la app quedan apagados hasta que el usuario mueva el interruptor. Si enciende uno, el hook de aprobación lo cubre igual (todo lo que no sea una lectura conocida pregunta). En Terminal llegan encendidos, sin interruptor por proyecto que Galeno controle. Las herramientas registradas en `.mcp.json` (WhatsApp, Slack, Notion, Jira, reuniones, Claude Design) no tienen ninguno de estos problemas: son del proyecto y cargan igual en los dos sitios.

### Diseño de la conexión con app propia (Fase 4, octubre 2026)

Al diseñar la Fase 4 se verificó contra las fuentes oficiales y varias suposiciones de arriba cambiaron. **Esta subsección manda sobre lo anterior donde lo contradiga** (en particular: la automatización del primer token y la rotación del token de Slack).

**Lo verificado**

| Hecho | Efecto |
|---|---|
| Google **no tiene API** para crear clientes OAuth: solo la consola. | La consola se resuelve con un agente de navegador o a mano; no hay atajo. |
| Google **bloquea el inicio de sesión en webviews embebidos** (`disallowed_useragent`, desde 2021). | Nada de `WKWebView`; además sería escribir contraseñas dentro de Galeno. |
| Chrome ≥ 136 ignora `--remote-debugging-port` sobre el perfil real. | No se controla Chrome por DevTools sobre la sesión del usuario. |
| Una app OAuth de Google en modo **Testing** emite refresh tokens que **caducan a los 7 días**. | **Decidido: publicarla "En producción" sin verificar** (una advertencia al autorizar, tope de 100 usuarios, sin caducidad semanal). Con Workspace de empresa: tipo **Interna**. |
| Los MCP de Google Workspace están en **Developer Preview** (hay que pertenecer al programa), con cliente tipo **aplicación web** y scopes `gmail.readonly`/`gmail.compose`, `drive.readonly`/`drive.file`, `documents*`, `spreadsheets*`. | Inscribirse en el programa es un paso manual. Por defecto se piden solo los de lectura; los de escritura solo si las reglas del usuario permiten escribir. |
| Slack solo permite MCP a apps **internas o del directorio**, y **el administrador debe aprobar** el cliente MCP. El interruptor «Model Context Protocol» (página *Agents & AI Apps* de la app) tiene campo de manifiesto: `settings.is_mcp_enabled` (referencia del manifiesto). **Comprobado con una app real:** sin él, Slack acepta la autorización y luego rechaza la conexión con «App is not enabled for Slack MCP server access». | Un PM sin rol de admin se bloquea: pantalla "Pide aprobación a tu administrador" con un mensaje listo para copiar. El manifiesto de Galeno lleva `is_mcp_enabled: true`; si aun así falla, Galeno dice dónde activarlo (`api.slack.com/apps/<id>/app-assistant`). |
| `claude mcp add` acepta `--client-id`, `--callback-port` y `--client-secret`; el secreto se toma de `MCP_CLIENT_SECRET` **sin terminal**, y queda en el llavero (no en `~/.claude.json`). | El secreto viaja solo por el entorno del proceso. |

**Lo decidido**

- **Principios:** contraseñas, 2FA y CAPTCHAs siempre los hace el usuario; **el modelo nunca ve un secreto**; aceptar términos, publicar la app, "Crear" el cliente y cada "Permitir" los confirma el usuario; todo paso automático tiene su equivalente manual; nada se persiste ni sale de la máquina salvo el `client_id`; detener siempre disponible.
- **Slack, hoy (implementado): el usuario solo inicia sesión.** Galeno abre **su propia ventana** (`WKWebView`) con `api.slack.com/apps`; el usuario se autentica ahí y Galeno pulsa «Generate Token», **elige el workspace en el que el usuario acaba de entrar** (lo sabe por el identificador que Slack anuncia en el enlace `slack://…`, que la ventana reconoce y no abre; el desplegable de Slack es propio, no un `<select>`; si ninguna opción coincide, pregunta) y **captura el token directo a memoria** (del texto o los atributos de la página, de la respuesta que lo genera o del botón «Copy», que se intercepta para que no llegue al portapapeles del sistema). Si un clic automático falla porque Slack cambió la pantalla, el usuario pulsa él mismo en esa ventana y la captura funciona igual. Al reconocer ese `slack://` la ventana vuelve a la página de tokens; las rutas `app.slack.com/t/<equipo>/login/…` se dejan terminar (interrumpirlas deja la sesión sin completar). No hay camino de «pegar el token a mano». **La autorización de la app también ocurre en Galeno** (decidido por Rafa tras ver que obligaba a entrar dos veces y dejaba una pestaña abierta en su navegador): `claude mcp login` abre la página de «Permitir» con `$BROWSER` (comprobado: lo respeta); Galeno le da un «navegador» que solo anota la dirección y la muestra en una segunda ventana con la **misma sesión efímera**, y la cierra sola cuando carga `http://localhost:51820/callback`. Solo `https` de `slack.com` y esa vuelta exacta; lo que no sea de Slack va al navegador del sistema. Una barra de 4 pasos con texto de lo que hace Galeno (y de cuándo es el turno del usuario) acompaña todo el proceso. Garantías: sesión **efímera** (no queda nada en el disco); el script **solo actúa en `api.slack.com`** (en las páginas de contraseña no hace nada); solo se aceptan mensajes del documento principal de ese sitio; la ventana navega solo por `https` y muestra siempre el dominio. La ventana se identifica como el Safari del sistema (Slack rechaza un WebKit anónimo: «your browser is not supported»), y **el inicio de sesión de Google se bloquea a propósito**: Google no lo permite en ventanas embebidas y no se esquiva; a esos usuarios se les dice que usen «Sign in with email» (Slack envía un código). Para saber que ya hay sesión se mira que **exista** la cookie `d` de Slack, sin leer su valor. Respaldo: generar el token a mano y pegarlo en un campo seguro. Después, en los dos casos: `apps.manifest.validate` (comprueba el token sin crear nada) → `apps.manifest.create` → `claude mcp add --client-id --callback-port --client-secret` con el secreto en `MCP_CLIENT_SECRET` → `claude mcp login`. El **token de configuración no se guarda ni se rota** (cambia respecto a lo anterior): una app por workspace, compartida por todos los agentes. Un servidor homónimo que no sea el nuestro (por ejemplo uno local de `npx`) ni se pisa ni se da por conectado.
- **Agente de navegador con Claude (`claude --chrome`): probado y descartado para Slack.** Cowork no tiene API; lo programable es `claude -p --chrome`, que habla con la extensión por un puente en la nube de Anthropic. Se probó 4 veces contra una réplica local de la página de tokens y **falló las 4**: en Arc crear la pestaña se cuelga 60 s, la extensión de Chrome no conectó, con `haiku` no puede abrir pestañas (no hay "auto mode") y cada intento fallido costó **$0,22–0,37 y 75–150 s**. Además exige Chrome/Edge/Brave, la extensión y un plan de pago, y el modelo vería la página. Puede volver a evaluarse para la consola de Google, donde no hay un token que capturar y un agente sí aporta.
- **Google (implementado, por los conectores de Claude).** Se descartó que cada cliente trajera su app de Google Cloud: verificado contra `developers.google.com/workspace/guides/configure-mcp-servers` y `/workspace/preview`, los servidores de Google siguen en **Developer Preview**, que exige inscribir el proyecto de Cloud en su programa, con **aprobación manual de «un par de días»** y solo para cuentas de **Google Workspace** (las `@gmail.com` personales no figuran como elegibles), además de activar 8 APIs con sus servicios MCP, la pantalla de consentimiento y el cliente OAuth. No cabe en un asistente. Tampoco se puede hacer «como Slack» en una ventana propia: Google bloquea el inicio de sesión en ventanas de apps. **Solo el conector de Drive se ha visto en una cuenta real**; de Gmail, Docs, Sheets y Calendar se usan el nombre del directorio y las herramientas que documenta Google, y la generación avisa con `unverifiedEndpoint` (si el nombre real fuera otro, ninguna regla coincidiría y Claude Code preguntaría por todo). Gmail: leer no pregunta; crear un borrador o etiquetar, sí. Docs y Sheets: leer no pregunta; editar sigue la regla del paso «Reglas». Calendar: leer no pregunta; crear, cambiar o borrar un evento, o responder a una invitación, **siempre** pide aprobación (les llega a los invitados: `ExternalSend.calendarEvent`). En todos, lo que no esté en sus listas lo detiene el hook. **Permisos del conector de Drive** (sus 11 herramientas vistas en una cuenta real): las 6 que leen van a `allow`; `create_file`, `update_file` y `copy_file` siguen la regla de Docs/Sheets del paso «Reglas»; `share_file` y `trash_file` **siempre** piden aprobación (regla `ask` y hook), igual que cualquier herramienta que el conector añada después. Los subagentes no reciben compartir ni papelera. **Sin comprobar:** el recorrido de «no está en la cuenta» de principio a fin y si el conector acepta cuentas `@gmail.com`. **Pendiente de decidir:** el agente hereda **todos** los conectores de claude.ai del usuario (no solo los de Google), fuera del hook de Galeno; Claude Code permite apagarlos por proyecto (`disableClaudeAiConnectors`, `deniedMcpServers`).

## 4f. Actualizaciones · arquitectura de 3 capas + Sparkle

**Política de negocio:** actualizaciones **de por vida, gratis** para quien compró. Pago único, sin renovación. Internamente se distingue (aunque todo sea gratis): el *mantenimiento* —bug fixes, parches del bridge de WhatsApp cuando Meta cambia su protocolo, compatibilidad con cambios de Claude Code y de los MCP— es una obligación perpetua; las *features nuevas* son gratis por elección. La distinción no cambia nada para el usuario; sirve para razonar costos a futuro. El mecanismo técnico es el mismo cualquiera sea la política, así que esta decisión no ata la arquitectura.

**Galeno se actualiza en 3 capas independientes:**

| Capa | Qué contiene | Cómo se actualiza |
|---|---|---|
| 1 · App Mac (Swift) | Wizard, UI, motor de config | **Sparkle**: la app revisa un appcast (XML) en el servidor, avisa al usuario, descarga el build firmado y se reemplaza con un clic. Soporta deltas (solo lo que cambió). |
| 2 · Bridge de WhatsApp (Go) | Puente whatsmeow + MCP (lectura y `send_message` con aprobación) | Viaja empaquetado en la .app, así que se actualiza vía Sparkle con ella; **al abrir, la app nueva pasa la copia instalada y el servicio de fondo a la versión que trae** (abajo, «Implicación para la app»). **Tiene su propio número de versión** para poder sacar un parche urgente del bridge sin re-releasear toda la app. Es la capa que más se rompe por causas externas (Meta). |
| 3 · Skills, catálogo y config | Las skills del perfil PM, el catálogo curado, prompts, plantillas | **Remoto, sin reinstalar.** La app las descarga del servidor/repo al configurar el agente y ofrece "actualizar skills" a usuarios existentes. Mejorar una skill o agregar una nueva NO requiere nuevo build de la app. Es lo que mantiene a Galeno vivo entre releases. |

**Sparkle — detalles que importan:**
- Framework open source estándar para apps Mac fuera del App Store.
- Actualizaciones **firmadas con clave EdDSA propia** (además de la firma de notarización de Apple): nadie puede inyectar una versión falsa. Crítico porque Galeno maneja tokens del usuario.
- El appcast, los DMG y las skills remotas se sirven desde la **misma infraestructura que ya existe** para el sitio y el webhook de Stripe. No es infraestructura nueva.

**Cómo quedó construido (Fase 8, 6 oct 2026).** Sparkle 2.10.0, fijado a esa versión exacta. La app mira el appcast **al abrir** y desde «Buscar actualizaciones…» (menú Galeno y Ajustes, que también dice la versión). **La petición no lleva perfil del sistema ni ningún dato del usuario** (`SUEnableSystemProfiling` en falso; `UpdatesModel`): solo lo de cualquier petición web y el nombre y la versión de la app, y la dirección no lleva parámetros. La clave EdDSA se generó una vez: la privada vive en el llavero de quien publica (cuenta `galeno`) y la pública en `GalenoApp/Galeno-Info.plist`. `scripts/build-release.sh` firma las piezas de Sparkle, firma el disco con esa clave y actualiza `site/public/appcast.xml` con las notas de la versión, que dicen qué versión del bridge lleva y **si cambió**. **La dirección del appcast es `https://getgaleno.com/appcast.xml` desde el 10 oct 2026** (antes, de relleno: `https://galeno.invalid/…`; con una de relleno la app no arranca Sparkle y el script se niega a entregar salvo que se le pida). La ventana de «hay una versión nueva» es la estándar de Sparkle y sale en el idioma del sistema, no en el de Galeno. Paso a paso: `docs/RELEASE.md`.

**Dónde se sirven (decidido por Rafa, 8 oct 2026).** El sitio (`site/`, Astro estático en Vercel Pro, dominio `getgaleno.com`) sirve **el appcast** en `https://getgaleno.com/appcast.xml` y **el índice de skills remotas** en `https://getgaleno.com/skills/v1/index.json` (reservado; el formato y la firma son de la Fase 5, y un formato nuevo sería `/skills/v2/`, nunca se cambia el `v1`). Los discos viven en un bucket público de Supabase y se descargan por `https://getgaleno.com/download/Galeno-<versión>.dmg`, que **redirige** al bucket: el appcast lleva esa dirección propia, así que mañana se puede cambiar de almacenamiento sin tocar una sola app instalada. **Las tres rutas son solo descargas: no reciben ni piden dato alguno del usuario.** El sitio no usa cookies, analítica ni scripts de terceros.

**Por qué va en la v0.0.1 aunque se lance una sola versión:** si la primera app sale sin Sparkle, esos usuarios tienen una app que no sabe actualizarse, y sacar la v0.0.2 obliga a contactarlos uno por uno. El mecanismo debe venir desde el primer build. Montarlo después, con usuarios ya instalados, es mucho más caro.

**Implicación para el motor (capa 3):** las skills NO se hornean dentro del binario de la app; se cargan desde una fuente remota versionada. El motor de config debe leerlas de ahí, con un fallback local por si el usuario está sin internet al configurar.

**Implicación para la app (capa 2):** el bridge no corre desde dentro de `Galeno.app` sino desde su copia estable (§4, «Ruta estable del bridge»), y el servicio de fondo (`sync`, LaunchAgent `com.galeno.whatsapp-bridge`) sigue con el binario con el que arrancó. Que Sparkle reemplace la app no cambia ninguna de las dos cosas. Por eso, **cada vez que la app arranca** (`WhatsAppBridge.refreshAfterAppUpdate`), si hay una copia instalada y su `version` no es la del bridge empaquetado, la app la reemplaza y, **solo si el LaunchAgent estaba cargado**, corre `install-launchd` con la copia nueva (lo desactiva y lo vuelve a activar; hasta tres intentos) para que `sync` tome el binario nuevo. Así un parche urgente le llega a quien ya tiene WhatsApp vinculado sin que tenga que abrir Salud. Límites: sin copia instalada no hace nada (no instala ni vincula a quien nunca usó WhatsApp); nunca toca la sesión ni `messages.db` (solo corre `version` e `install-launchd`); «distinta» es distinta, no «más nueva» (volver a una app anterior también devuelve el bridge); y falla en silencio: no hay aviso ni pantalla, y lo que quede mal lo enseña Salud como lo encuentre. **Sin comprobar contra un WhatsApp real** (6 oct 2026): está probado con dobles, no con un `sync` de verdad conectado; ver la fila de `docs/QA.md` sobre actualizar con WhatsApp vinculado.

**Esto no contradice "nada sale a servidores nuestros":** las tres capas son *descargas* desde infraestructura propia hacia la máquina del usuario. Ni el appcast ni las skills remotas reciben tokens, contenido ni datos de uso.

## 4g. Cómo se entrega: firma, notarización y sin licencias (6 oct 2026)

- **Sin clave de licencia ni activación en la v0.0.1** (decisión de Rafa, 6 oct 2026): se vende como «paga, descarga y usa». Lo que se acepta a cambio es que quien tenga el instalador —o dé con la dirección del appcast de Sparkle, que es pública por fuerza— puede usar Galeno sin pagar; con los primeros usuarios pesa más no añadir una pantalla antes de empezar. La alternativa quedó construida y aparcada en la rama `feat/licencias` (clave firmada con Ed25519 comprobada en el Mac, prueba de 7 días), por si hace falta una prueba gratis o cobrar una versión mayor. Si llega a haber licencia, cubre **agentes ilimitados**.
- **El DMG va firmado con Developer ID y notarizado**, incluido el bridge de Go (`scripts/build-release.sh`, `docs/RELEASE.md`): hardened runtime en la app y en el bridge, firma de dentro hacia fuera, sello de tiempo, notarización del DMG con `notarytool`, grapado y verificación con `spctl`. **Entitlements vacíos**: fuera de la tienda y sin sandbox, la red y lanzar procesos no los piden, y Galeno no necesita ninguna excepción del hardened runtime.

## 6. Qué genera el motor (la config de Claude Code)

Para el perfil PM, el motor escribe en la máquina del usuario:

- `AGENTS.md` — identidad del agente, rol PM, la descripción del proyecto, qué herramientas tiene, reglas, y cómo usar la memoria.
- `.claude/settings.json` — `effortLevel: "low"` (decisión de Rafa, 4 oct 2026: el agente sobre todo lee y resume, y con esfuerzo bajo responde de 2 a 3 veces más rápido que con el `high` que el usuario suele traer; manda sobre su ajuste personal y `/effort` lo sube dentro de una sesión; **el modelo no se fija**, cada quien usa el de su plan) y reglas deny/ask/allow: envíos externos en `ask` (en Slack, las 14 herramientas de solo lectura van a `allow` por su nombre exacto, las 13 que envían o escriben a `ask`, y el hook de aprobación cubre todo lo del servidor que no sea una lectura conocida, también una herramienta que Slack añada después; las listas salen del servidor real, 4 oct 2026, y viven en `MCPServerCatalog`. Gmail sigue entero en `ask` hasta verificar las suyas; Google Drive: lecturas en `allow`, escrituras según la regla, compartir y papelera siempre en `ask`), nada de ejecutar código, `Edit(/memoria/**)` en `allow`, y en `deny` por nombre lo que el motor genera fuera de `memoria/`. (Un patrón que niegue todo el proyecto y deje `memoria/` como excepción no funciona: probado contra Claude Code, la excepción `!` no reabre un directorio bloqueado entero.)
- `memoria/` — las notas del proyecto que mantiene el agente (§3b). El motor la crea si no existe y **nunca la sobrescribe** al regenerar.
- `.mcp.json` — los MCP conectados (WhatsApp, Slack, Notion, Jira, Fireflies/Granola/Fathom, Claude Design; **Gmail y Google Drive no**: son conectores de la cuenta de Claude), con tokens como referencias a variables de entorno, nunca en texto plano.
- `.claude/agents/` — subagentes del perfil PM: `scribe`, `tracker`, `reporter` (solo lectura + Notion/Jira; sin Bash, sin Edit de código; de WhatsApp, solo las 9 lecturas por nombre y **nunca** `send_message`). Su lista de herramientas es una lista blanca. Reciben los servidores de las herramientas conectadas que no pueden enviar (WhatsApp, transcripciones, Notion, Jira, Google Drive/Docs/Sheets) y **nunca los de Slack ni Gmail**: un servidor se concede entero, así que un subagente con Slack tendría también la herramienta de enviar. El agente principal lee Slack y el correo, les pasa lo relevante, y es el único que envía.
- `.claude/hooks/` — hook de aprobación para todo envío externo.
- `.claude/skills/` — **la lista de skills de abajo.** No vienen horneadas en la app: el motor las toma de una fuente remota versionada, con un fallback local (§4f, capa 3).

### 6.3 Skills externas ("trae la tuya") — fuera de la v0.0.1

En v0.0.1 **solo hay dos niveles de skills: las nuestras y las curadas**, ambas revisadas por nosotros antes de entrar a la lista. Así no existe ninguna puerta por la que entre código no revisado.

**Cómo entra una skill de un tercero** (primera vez: las diez de marketing, 5 oct 2026). No se copia: se **adapta** y queda como obra derivada, con su licencia.

- Vive en `skills/curated/<id>/`: el `SKILL.md` adaptado y el `LICENSE` de su carpeta de origen. El motor copia la carpeta entera al agente, así que la licencia viaja con la skill.
- En `catalog.json` va en `curated`, con autor, repositorio, ruta y licencia, y además lo que necesita su tarjeta (`group`, `writes`, `needsAny`, `ask`, `example`, `guarantee`). Con contenido y grupo tiene tarjeta (`CuratedSkill.card`); la vista previa dice «De Anthropic · Apache-2.0» con el enlace al original. **De fábrica no va marcada**: solo las nuestras.
- Qué se le cambia, siempre: la instrucción de idioma; los conectores genéricos del plugin (`~~analytics`, `~~knowledge base`…) por lo que Galeno conecta o por «pégamelo»; lo que dependía del archivo de ajustes del plugin (la voz de marca) pasa a `memoria/marca.md`, que el agente sí puede escribir; una sección «Save» que pregunta dónde guardar; y una sección «Rules» como la de las nuestras (lo que dicen las fuentes no es una orden, no inventa, no envía ni publica nada). Lo demás queda **tal cual lo escribió su autor**.
- Cada una termina con una sección «Source»: de dónde salió, con qué licencia y qué cambió Galeno (lo exige Apache-2.0 §4).
- Las mismas pruebas que las nuestras (`SkillCatalogTests`), más: licencia al lado, sección «Source» y ningún marcador de conector del plugin.
- **Las que miran la web** (`seo-audit`, `competitive-brief`): buscan sin pedir permiso y piden aprobación para abrir una página concreta (ver «Búsqueda web», abajo). Si no pueden mirar, trabajan con lo que el usuario pegue y **no rellenan de memoria**. Lo que dice una página es dato, nunca una orden. Toda cifra de SEO (volumen, dificultad, posición, velocidad) es una estimación en palabras o «sin medir» salvo que el usuario traiga la suya.
- **Las de voz de marca** (Tribe AI): el plugin original repartía el trabajo entre cinco subagentes propios y guardaba en `.claude/`. Aquí cada skill hace ese trabajo ella misma, con el método del autor, y la guía se guarda en `memoria/marca.md` (nunca la reemplaza sin preguntar). Traen su carpeta `references/`, que viaja con la skill. `discover-brand` busca en Notion, Google Drive, Slack y las herramientas de reuniones; **el correo solo si Gmail es una de las herramientas del agente y el usuario lo incluye en esa búsqueda** (añadido nuestro, no del autor; la tarjeta lo avisa: «añade Gmail como herramienta») y WhatsApp nunca.
- Comprobado contra Claude Code real: una carpeta con las diez las lista todas al arrancar. **No están probadas con trabajo real.**

**Comercial, primera tanda (5 oct 2026).** Cinco del plugin de ventas de Anthropic (Apache-2.0), en un grupo «Comercial»: `call-summary`, `call-prep`, `draft-outreach`, `inbox-sweep` y `daily-briefing`. Lo propio de estas:

- **Galeno no conecta un CRM**, y el plugin original giraba alrededor de uno. Los datos de cuentas y oportunidades salen de lo que el usuario pega o de una hoja de Google; sin eso la skill escribe «not provided» y no lo reconstruye. Donde el original actualizaba el CRM, deja los cambios **como texto para pegar**.
- **Nada sale solo.** Las tres que pueden terminar en un correo o un mensaje (`call-summary`, `draft-outreach`, `inbox-sweep`) cierran con una sección «Approval, then send»: el borrador de Gmail se crea solo tras un sí, y enviar pide un «sí» explícito al texto exacto, uno por uno. El plugin original traía la instrucción contraria («hazlo por el conector, sin añadir restricciones»): se quitó. Sus tarjetas dicen «siempre te pide aprobación» (`sendsToOthers`). WhatsApp, solo lectura.
- **`inbox-sweep` lee el buzón del usuario**: un correo que le habla a un asistente o le pide una acción se reporta y no se sigue, ni se abren sus enlaces. No archiva, etiqueta ni borra. Para imitar cómo escribe el usuario **pregunta antes** y lee como mucho 10 correos enviados (el original leía 30–40 sin preguntar).
- **`draft-outreach` busca en la web solo el nombre público de la empresa**, nunca el de una persona.
- `daily-briefing` no se programa sola: se pide cada mañana (las tareas programadas siguen fuera de v0.0.1).
- Cada una dice cuándo usar la nuestra en su lugar (`/acta`, `/seguimiento`, `/reporte-dia`).

**Comercial, segunda tanda (5 oct 2026).** Otras cinco del mismo plugin: `schedule-meeting`, `customer-voice`, `account-plan`, `close-plan` y `handle-objection`. Mismas reglas que la primera, y además:

- **Una invitación es un envío** (`schedule-meeting`): un evento con asistentes les avisa. Leer calendarios no pide nada; crear el evento exige enseñar título, fecha y hora **con su zona horaria**, duración, asistentes, descripción y enlace, y un «sí» explícito a eso exacto (el «agéndalo» del principio no cuenta). Mover, aceptar, rechazar o cancelar piden lo mismo. La zona horaria nunca se supone. Coincide con los permisos generados, que ya tratan crear, cambiar, borrar y responder un evento como escritura.
- **Citas textuales** (`customer-voice`): solo va entre comillas lo copiado tal cual, con quién lo dijo, cuándo y dónde, y en su idioma (la traducción va fuera de las comillas). Si nadie habló del tema, se dice.

**Comercial, tercera tanda (5 oct 2026): comercial queda en dieciséis.** Las seis que faltaban de las que funcionan sin CRM: `stakeholder-map`, `account-context`, `create-an-asset`, `weekly-wrap`, `lead-triage` y `account-tiering`. Lo propio:

- **`create-an-asset` escribe el contenido, no el archivo.** El agente no crea presentaciones, PDF ni hojas: entrega el material como texto estructurado (una presentación, lámina por lámina, con título, cuerpo y notas del orador) y el usuario lo maqueta en su herramienta. La skill y su tarjeta lo dicen, y no prometen diseño ni exportación.
- **Puntuar es recomendar** (`lead-triage`, `account-tiering`): los criterios (cliente ideal, pesos, cortes) son del usuario; si no hay, se preguntan y cualquier borrador va rotulado como propuesta. Un dato que falta es «datos insuficientes», no una mala nota. La cuenta se hace a mano y se enseña. La skill nunca descarta, reasigna ni contacta. Un formulario de lead es justo donde un extraño puede plantar instrucciones: se reporta y no cambia el puntaje.
- **Personas** (`stakeholder-map`, `account-context`): roles y posturas salen de los registros, llamadas e hilos del usuario, con fuente y fecha; un cargo no se adivina ni se busca a nadie en la web; lo deducido va marcado como inferencia, y nada personal ni sensible.
- Las tres que pueden terminar en un mensaje de Slack (`account-context`, `weekly-wrap`, `lead-triage`) llevan la misma sección de aprobación. `weekly-wrap` no se programa sola.

**Comercial, las nuestras.** `/prospeccion` (6 oct 2026): a quién escribirle hoy y por qué, con el mensaje en la voz del usuario. **Desde el 7 oct 2026 (`docs/09` §7.5) ofrece enviarlo con aprobación** por `send_message`; el enlace `https://wa.me/<número>?text=<mensaje>` —que abre WhatsApp con el mensaje escrito y no envía nada— queda como respaldo para chats `@lid` sin número, topes alcanzados o preferencia del usuario. Dos fuentes de prospectos: (a) los chats del propio usuario (conversaciones que se enfriaron, alguien que preguntó en un grupo, una promesa sin cumplir); (b) prospectos nuevos de la web, solo si el usuario pide un segmento: la búsqueda lleva el segmento y la ciudad y nada más, y **el número solo si está publicado para negocios**: el que la propia empresa da como canal para clientes, o el de un contacto comercial con nombre publicado en un contexto de negocio (su sitio, el directorio de un gremio o de una feria, una ficha legal; decisión de Rafa, 7 oct 2026). Nunca el personal de alguien sacado de redes, de un buscador de personas, de un foro o de una noticia, ni uno deducido. Deja `memoria/informes/prospeccion-<fecha>.html` y su gemelo `.md`. **Las cuatro del plan de Simon (`docs/09` §7, PR 5):** `/prospectar-lista` (prospectar desde una lista en Google Sheets: califica con el criterio del usuario, investiga el sitio con `WebFetch`, corre su radiografía, escribe el primer contacto y lo anota todo en la misma hoja; con el usuario delante envía uno por uno con aprobación, programada deja `Mensaje propuesto` y borradores de Gmail), `/seguimientos-hoy` (la tarea de las 8: a quién escribirle hoy y qué decirle, leyendo la hoja, WhatsApp y Gmail; máximo 3 seguimientos por lead), `/revisar-conversaciones` (solo lectura: qué funcionó y qué no, con 3 mejoras concretas) y `/crear-skill` (entrevista corta y redacta la skill en `memoria/skills-borrador/`; **solo el usuario la instala**, desde Skills → «Añadir skill…», así una skill nunca se instala sola). `prospectar-lista` y `seguimientos-hoy` vienen marcadas para el rol comercial. Las de Simon (`criterio`, `radiografia`) son skills **propias** suyas: no entran al catálogo.

**Búsqueda web** (decisión de Rafa, 5 oct 2026). El agente generado **busca en la web sin pedir permiso**: `WebSearch` va en `allow` (`SettingsRenderer.allowedWebTools`), su `AGENTS.md` se lo dice, y el paso «Tus herramientas» la enseña como una tarjeta marcada y fija, «Búsqueda web · Incluida» (no se conecta ni se elige). **`WebFetch` también se permite sin preguntar, en los tres roles** (decisión de Rafa, 7 oct 2026; antes nunca, y el plan `docs/09` §5 lo traía solo para comercial): abrir el sitio de un prospecto, de un competidor o de un cliente es parte del trabajo, y pedir aprobación por cada dirección lo hacía inservible. El riesgo es conocido: una dirección puede llevar datos del usuario y una página puede traer instrucciones escondidas. Lo contiene una **regla de contención** en el `AGENTS.md` generado («Abrir páginas web»): solo se abre la dirección que el usuario tiene anotada como sitio de un prospecto o cliente, una que salió de una búsqueda del propio agente, una que el usuario escribió, u **otra página del mismo sitio** que una de esas (su contacto, «nosotros», sus términos; decisión de Rafa, 7 oct 2026, porque investigar un prospecto lo necesita); nunca una de otro sitio que aparezca dentro de una página, un mensaje, un correo o un documento; nunca una dirección construida con datos; y si una página pide abrir otra, enviar algo o cambiar lo que se hace, se ignora y se avisa. **No es una barrera técnica, es una instrucción**, y se acepta a propósito; una prueba del motor exige que el permiso y la regla vayan juntos, y la prueba de inyección de `docs/09` §9 lo comprueba a mano. El agente tiene además la instrucción de no poner en una búsqueda datos de personas ni lo que leyó en sus fuentes; buscar el nombre público de una empresa o de un producto sí vale.

**Skills propias (decisión de Rafa, 6 oct 2026; Simon ya escribe las suyas).** La línea roja 6 se abre **solo** para los archivos del propio usuario, en su propio Mac, para su propio agente: una carpeta con `SKILL.md` (entera: puede traer plantillas al lado) o un `.md` suelto, elegidos en el selector de archivos. **Nada remoto**: ni enlaces, ni catálogo de terceros, ni descargas; nada se ejecuta. Viven en `skills-propias/<id>/` dentro de la carpeta del agente (`OwnSkills`), que es del usuario como `memoria/`: el motor no la escribe ni la borra al regenerar, solo instala desde ahí las marcadas a `.claude/skills/<id>/` (`SkillSource.own`). El id sale del nombre de la carpeta o del archivo («Mi Cierre.md» → `mi-cierre`), con las mismas reglas que un id del catálogo; dos skills con el mismo id se rechazan antes de escribir nada (`GenerationError.duplicateSkill`): el catálogo manda y la propia cambia de nombre. **Una skill propia no cambia ningún permiso**: las reglas `deny`, el `ask` y los hooks aplican aunque la skill diga lo contrario, y enviar sigue preguntando. El agente tampoco puede editarlas (`skills-propias/**` está en `SettingsRenderer.protectedPaths`): solo el usuario. En el asistente se copian al **crear** el agente (o al **guardar** en «Gestionar»); un borrador no las guarda (no sabe de dónde copiarlas) y al reanudar vuelven sin marcar. Quitar una que ya estaba en la carpeta la manda a la **Papelera** al guardar, nunca la borra. La vista previa dice «Tuya», sin ejemplo. Lo que el motor **no** hace, a propósito: inspeccionar el texto de la skill (es del usuario; el guardrail son los permisos, no un filtro). **Sin probar con una skill real de Simon.**

El nivel "trae la tuya" (pegar un link de GitHub) se pospone. Cuando se añada, tendrá que traer este guardrail: una skill le dice al agente cómo comportarse, y una maliciosa puede intentar que ignore sus reglas o envíe datos afuera (prompt injection servido en bandeja). Reglas mínimas para esa versión futura: advertencia explícita antes de instalar; una skill nunca eleva permisos (las reglas `deny`, el `ask` y el hook aplican aunque la skill diga lo contrario); el motor inspecciona el SKILL.md y rechaza instrucciones de exfiltrar datos o desactivar reglas; y registro del origen de cada skill instalada.

**Lo que ninguna de estas trae y es tu diferencial:** la integración con **WhatsApp** y la **separación por proyecto** (futura). Las skills de PM existentes asumen un solo producto y herramientas de escritorio; tú añades el mundo de LatAm (WhatsApp) y el multi-cliente.

## 8. Riesgos específicos de la v0.0.1

| Riesgo | Mitigación |
|---|---|
| Ban de WhatsApp a un usuario | Aprobación por mensaje, topes y espaciado en el código, sin listas de difusión, grupos solo con su nombre comprobado, pausa, advertencia explícita, correo primero para el frío, y sin promesa de "seguro" (`docs/09` §10) |
| Tokens expuestos | Nunca en texto plano; referencias a env; nunca en servidores propios |
| Agente envía algo mal a un cliente | Todo envío externo en `ask` + hook de aprobación |
| Apple bloquea la app (Gatekeeper) | Firmar y notarizar el DMG desde el inicio; el binario Go embebido también debe firmarse |
| Meta rompe el protocolo de WhatsApp | El bridge deja de leer; se saca parche urgente de la capa 2 vía Sparkle (por eso tiene versión propia). Mantenimiento de por vida, no opcional |
| Claude Code cambia formato de config | Motor desacoplado; actualizaciones como parte del soporte |
| Usuario no técnico se traba en un OAuth | Cada pantalla con captura de qué hacer y botón de "ayuda" |
